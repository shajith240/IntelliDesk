Database Design & Migrations

Why the schema looks the way it does: the normalization decisions, how tenant isolation is enforced by the database itself, how invariants live in constraints and triggers instead of application code, and the history of all 13 migrations including how they were applied to a live database without downtime. For the table-by-table reference, see Data Model & Schema.

Design principles

What is the one-sentence philosophy of this schema?Basic

Every rule that must always hold is enforced by the database, not only by the application: tenant boundaries by composite foreign keys, the ticket workflow by a transitions table and a trigger, multi-step operations by transactional functions, and derived values are either not stored or computed by the database (generated columns). Application code can have bugs; a constraint can't be skipped.

The concrete consequence is that the schema is tested directly: 45 checks in supabase/tests/ try to break each rule (cross-tenant writes, invalid transitions, editing the audit log) and assert the database refuses.

supabase/tests/*.sql (5 suites, 45 PASS checks — see testing.html)
How is multi-tenancy isolated at the database level, not just in queries?Advanced

Every tenant-owned table has a non-null organization_id. Parent tables expose a composite unique key (id, organization_id), and child tables reference it with a composite foreign key. A row therefore cannot point at a row of another organization even if application code passes the wrong id: the pair (foreign_id, my_org) simply doesn't exist in the parent.

ALTER TABLE public.users    ADD CONSTRAINT users_id_org_key    UNIQUE (id, organization_id);
ALTER TABLE public.teams    ADD CONSTRAINT teams_id_org_key    UNIQUE (id, organization_id);
ALTER TABLE public.tickets  ADD CONSTRAINT tickets_id_org_key  UNIQUE (id, organization_id);
ALTER TABLE public.accounts ADD CONSTRAINT accounts_id_org_key UNIQUE (id, organization_id);
ALTER TABLE public.emails   ADD CONSTRAINT emails_id_org_key   UNIQUE (id, organization_id);
supabase/migrations/007_integrity_and_assignment.sql:15-32

The same pattern is used for every later relationship: ticket messages, citations, AI credentials, spam overrides, the audit log. The test suites include explicit cross-tenant attempts (assigning another org's admin, attaching another org's email to a conversation, citing another org's article) that must fail with foreign_key_violation.

supabase/tests/assignment_integrity.sql (1b, 6); supabase/tests/normalization.sql (4)
Why use the service-role key and close the Supabase Data API instead of writing RLS policies?Advanced

Authentication is NextAuth (JWT), not Supabase Auth, so auth.uid() is always null for the app's users and the RLS policies written in 003 could never work. The real threat was the opposite: before 006, anon and authenticated had full privileges with RLS disabled, so anyone with the public anon key could read password hashes and mailbox credentials through PostgREST.

Migration 006 made the database closed-by-default: RLS on everywhere with no policies, all privileges revoked from anon/authenticated (also for future objects via default privileges), and only service_role — used exclusively on the server — can read or write. Every later migration repeats the revoke/grant for its new objects.

supabase/migrations/006_lockdown_public_api.sql:1-14, 55-63

If derived data is bad, why is tickets.ai_confidence still a column?Advanced

Because it is used for sorting and averaging on every dashboard load, so it is worth storing — but it is now a generated column that Postgres computes from the stored AI verdict. It can be read and indexed like a column but can never be written or disagree with its source. Before this change, 14 seeded tickets had a confidence value that did not match their (missing) verdict; 012 rebuilt the verdict from those rows before 013 made the column generated.

ALTER TABLE public.tickets
  ADD COLUMN ai_confidence real
    GENERATED ALWAYS AS ((ai_classification ->> 'confidence')::real) STORED;
supabase/migrations/013_normalize_contract.sql:264-266; 012_normalize_expand.sql (section 6)

This is "controlled denormalization": redundancy the database maintains, versus redundancy the application must remember to maintain. The test conversation_model 11 proves a direct write fails with generated_always.

Where is the schema deliberately not normalized, and why?Intermediate
  • tickets.ai_classification (JSONB) — a snapshot of what the AI said when the ticket was created. The category/severity columns hold the current values, which people may change; the JSON is history, so it is not a duplicate.
  • emails.to_address, cc (text) — emails is the raw transport log and keeps headers as received. It is never queried by recipient except for the auto-reply rate limit, which has its own partial index.
  • ticket_messages.body_text vs emails.body_text — the message holds the cleaned conversational text (quoted history stripped, HTML converted); the email keeps the raw body for re-processing and forensics. Different data produced by a non-trivial transformation, not a copy.
  • audit_logs.details (JSONB) — event payloads vary by action; an audit log is append-only history, not queried relationally.
README.md "Normalization decisions"; supabase/migrations/011_ai_settings_and_spam_review.sql:50-52
Why is user email globally unique but contact email only unique per workspace?Intermediate

Users (staff) sign in with just an email and password — there is no workspace picker — so one email must identify exactly one account: UNIQUE (lower(email)) on users. Contacts (customers) are data owned by a workspace: the same person may email two different companies that both use the product, so contacts are unique on (organization_id, lower(email)). The old global contacts_email_key prevented that and was dropped in 012, together with a redundant case-sensitive users_email_key.

supabase/migrations/007_integrity_and_assignment.sql:37; 012_normalize_expand.sql:81-91; supabase/tests/normalization.sql (check 3)
How are ticket numbers generated, and why not a sequence?Advanced

Originally one global sequence produced TKT-00031, TKT-00087… across all tenants, which leaks each tenant's ticket volume to the others. 012 replaced it with a ticket_counters row per organization, incremented by an upsert inside the insert trigger. The row lock taken by ON CONFLICT DO UPDATE serializes concurrent inserts within one organization only, and numbers are unique per (organization_id, ticket_number).

INSERT INTO public.ticket_counters AS c (organization_id, last_number)
VALUES (NEW.organization_id, 1)
ON CONFLICT (organization_id) DO UPDATE SET last_number = c.last_number + 1
RETURNING last_number INTO v_next;
NEW.ticket_number := 'TKT-' || lpad(v_next::text, 5, '0');
supabase/migrations/012_normalize_expand.sql:16-48

Trade-off: a sequence never blocks, while the counter row serializes one tenant's ticket inserts. At helpdesk volumes (tickets per second, not thousands) that is irrelevant, and gap-free per-tenant numbers are what users expect.

Invariants enforced by the database

How is the ticket status workflow enforced?Advanced

Statuses are rows in a lookup table (ticket_statuses, with is_open) and the allowed moves are rows in ticket_status_transitions; tickets.status is a foreign key to the lookup instead of a CHECK list. A BEFORE UPDATE OF status trigger rejects any move that isn't a row in the transitions table, and owns sla_resolved_at: set when a ticket leaves the open statuses, cleared when it's reopened, kept when Resolved becomes Closed.

How does a single constraint guarantee that a customer message never points at an outgoing email?Advanced

ticket_messages has a generated column email_direction derived from kind (customer → inbound, reply → outbound). Its foreign key is (email_id, organization_id, email_direction) referencing emails (id, organization_id, direction). One declarative constraint checks the same tenant and the right direction — no trigger needed.

email_direction text GENERATED ALWAYS AS (
  CASE kind WHEN 'customer' THEN 'inbound' WHEN 'reply' THEN 'outbound' END
) STORED,
...
CONSTRAINT ticket_messages_email_fkey FOREIGN KEY (email_id, organization_id, email_direction)
  REFERENCES public.emails (id, organization_id, direction),
supabase/migrations/009_conversation_model.sql:131-165

A real limitation surfaced while building it: Postgres forbids ON DELETE SET NULL on a foreign key containing a generated column. The key uses NO ACTION instead, which is arguably better — an email that is part of a conversation can't be deleted on its own; deleting the whole organization still cascades through both tables in one statement.

Supabase's JS client sends each call as its own HTTP request, so a sequence of inserts from the app cannot be one transaction. Putting multi-row invariants in a function is the only way to get all-or-nothing semantics and row locks. Each is tested for atomicity and single use (e.g. calling complete_ticket_reply twice fails).

How is the audit log made tamper-resistant when the app's own key can write anything?Advanced

A BEFORE UPDATE OR DELETE trigger raises insufficient_privilege unless the transaction explicitly opts in with SET LOCAL intellidesk.audit_maintenance = 'on' (for retention or deleting a workspace). The only change allowed without it is referential: when a user or ticket is deleted, its id is cleared from the audit row and nothing else changes — the trigger compares the new row to the old one with only those ids nulled.

IF TG_OP = 'UPDATE' THEN
  v_expected := OLD;
  IF NEW.actor_user_id IS NULL THEN v_expected.actor_user_id := NULL; END IF;
  IF NEW.ticket_id IS NULL THEN v_expected.ticket_id := NULL; END IF;
  IF NEW IS NOT DISTINCT FROM v_expected THEN
    RETURN NEW;
  END IF;
END IF;
supabase/migrations/012_normalize_expand.sql:102-146

012 also changed the audit log's ticket foreign key from ON DELETE CASCADE (deleting a ticket erased its history) to ON DELETE SET NULL (ticket_id). SET NULL (column) is Postgres 15+ syntax that nulls only the named column of a composite key, keeping organization_id intact.

supabase/migrations/012_normalize_expand.sql:139-141; supabase/tests/normalization.sql (check 5)
What other constraints encode business rules?Intermediate
  • enforce_ticket_assignee trigger: an assignee must be an active admin or agent of the same organization (viewers can't hold tickets).
  • ticket_messages_kind_shape CHECK: customer messages have no delivery state, replies always do, notes are never linked to an email; only agents carry a user id; a delivery error only exists when delivery failed.
  • emails_outbound_not_queued CHECK: outbound mail is always processed, so it can never enter the intake queue.
  • organizations.timezone CHECK: now() AT TIME ZONE timezone IS NOT NULL rejects zone names Postgres doesn't know.
  • ai_credentials: key hint exactly 4 characters; last_error only while status = 'error'.
  • emails_not_spam_pair: a spam override always has a timestamp.
  • accounts_org_domain_key: one company account per (organization, lower(domain)).

What is expand/contract, and how was it used here?Advanced

A schema change that removes or renames something breaks whichever code version isn't expecting it, and code and database can't switch at the same instant. Expand/contract splits the change so every intermediate state is compatible with the code running at that moment:

  1. Expand — add new tables/columns and relax constraints; old code keeps working. (012; also 007 and 009 kept the legacy text columns and ticket_emails.)
  2. Deploy code that uses only the new shape.
  3. Contract — drop what nothing uses any more. (013, applied only after the deploy succeeded.)

During the 009 window the old pipeline still wrote only ticket_emails, so 009 installed a temporary bridge trigger copying each such link into ticket_messages; 013 dropped the bridge with the table.

supabase/migrations/009_conversation_model.sql:221-245 (bridge); 012_normalize_expand.sql:1-3; 013_normalize_contract.sql:1-3, 248-250
How were migrations applied safely to a live database?Intermediate
  1. Rehearse: run the migration body plus every test suite inside one BEGIN … ROLLBACK against production. Nothing persists, but real data is checked (this is how the sla_policies_severity_check collision in 007 and the generated-column FK restriction in 009 were caught).
  2. Back up the affected tables (pg_dump --data-only).
  3. Apply with supabase db push, which records the version in the migrations history.
  4. Reload PostgREST's schema cache (NOTIFY pgrst, 'reload schema') so new relationships are visible to the API.
  5. Re-run every test suite against the live database.

Migrations are never renamed or edited after being applied; fixes go in a new migration.

What database-level limitations remain?Intermediate
Known limitations
  • PostgREST did not detect the self-referencing composite foreign key tickets.follow_up_of for embedding, so the API loads the parent ticket with a second query.
  • sla_policies.organization_id is nullable by design (NULL = global default policy, overridden per org).
  • No business-hours calendar or SLA pause while Pending (planned in the roadmap).
  • Free-tier Supabase has no automatic backups; backups were taken manually before each migration.
