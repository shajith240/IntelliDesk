Timeline & Roadmap

How the project evolved from a prototype into a multi-tenant product, phase by phase, what each phase delivered, and what is still to be built. Dates are from the git history.

How the project evolved

What was the starting point?Basic

A working prototype: an IMAP poller, a Gemini classifier, Pinecone-based FAQ matching, a Next.js dashboard, and a Supabase schema with 12 tables. It worked for a demo, but had one global mailbox in environment variables, an open database API, unauthenticated development routes, no roles beyond a label, and several ways to lose email. The UI was then rebuilt as a Jira-style support workspace, and the code reorganized into src/features and src/server.

How was each phase planned?Intermediate

Each phase started with research into how mature products solve the problem — Zendesk, Help Scout, Freshdesk and Front for ticket lifecycles, threading, SLAs and spam handling; the open-source Zammad, FreeScout and Chatwoot for data models; Intercom Fin and Zendesk AI agents plus the OWASP LLM Top 10 for AI safety; RFC 3834 for automatic replies — and an audit of the current code for gaps. Then: migration rehearsed against production, application code, database and unit tests, a scripted end-to-end run, and deploy.

What's next

What is planned for Phase D (users and operations)?Basic
  • Password reset: an admin resets a member's password (issuing a new one-time password), plus optionally an emailed, signed, single-use, short-lived reset link.
  • SLA done properly: business-hours calendars per workspace; pause the clock while a ticket is Pending; next-reply time in addition to first reply and resolution.
  • Notifications: email or in-app alert to admins when tickets land in Needs Review or near an SLA breach.
  • Workspace branding: company name and logo (Supabase Storage) in the app and in outgoing email.
  • Timezone setting in Settings (the column and dashboard logic already exist).
  • Auto-close: Resolved tickets become Closed after N days (Zendesk-style).
What else is on the backlog?Basic
  • Attachments: store them (Supabase Storage) and show them in the conversation.
  • Testing: commit the Playwright scripts as a suite and run all tests in a CI workflow on every push.
  • AI quality: report draft-vs-sent differences and agent feedback; per-topic auto-send settings; reply-language checks.
  • Routing: optional round-robin or capacity-based assignment for larger teams.
  • Encryption key rotation using the v1: ciphertext version prefix.
  • Operations: uptime monitoring, error tracking, automatic backups (Supabase Pro).
  • Gmail OAuth instead of app passwords, once Google verification is feasible.
  • Historical analytics (time series).
What are the current known limitations?Intermediate
Not implemented yet
  • No password-reset email and no two-factor authentication.
  • SLA uses wall-clock time and doesn't pause while Pending.
  • Attachments are ignored.
  • No notifications; Needs Review is visible only in the app.
  • No branding UI; outgoing mail uses the organization name only.
  • No committed end-to-end suite or CI test run.
  • Analytics show the current state, not trends.
  • One mailbox per workspace.
  • Real Gmail sending and threading hadn't been exercised in production when these docs were written (no mailbox connected yet).
What would it take to sell this to a real company?Intermediate

Technically: Phase D, Vercel Pro (commercial use) and Supabase Pro (backups), a privacy policy and data processing agreement, a status page, and a pilot with auto-send off. The business case is on Product & Business.
