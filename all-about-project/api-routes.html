API & Backend Routes

The 20 API endpoint handlers, focusing on the most complex: ticket CRUD, dashboard aggregation, email polling and processing, response sending, and FAQ management. All protected routes enforce authentication and organization-scoped filtering; webhook routes use bearer tokens. Three routes are dev-only and blocked in production.

Ticket Management

What does GET /api/tickets return and how does filtering work?Intermediate

Returns a paginated list of tickets for the authenticated user's organization. Supports filtering by status (New, In Progress, Resolved, Closed), severity (P1–P4), category, and search (in subject/ticket_number/summary). Pagination defaults to page 1, limit 20, max 100. Sorting is by created_at (default), updated_at, severity, status, or ticket_number. The response includes related contact and account objects via Supabase select joins.

SLA due dates are computed at read time if missing, by fetching sla_policies once and calculating created_at + policy_minutes for each ticket.

{
  "tickets": [...],
  "total": 42,
  "page": 1,
  "limit": 20,
  "total_pages": 3
}
src/app/api/tickets/route.ts:15-179 (GET handler with filtering, pagination, SLA fill-in)
What validation does PATCH /api/tickets/[id] perform on updates?Advanced

Only these fields are allowed to be updated: status, severity, category, assigned_team, assigned_agent, sla_first_response_at, sla_resolved_at. Status is validated against the enum [New, In Progress, Resolved, Closed]; severity against [P1, P2, P3, P4]. If assigned_agent is set to a non-null user ID, a lookup query checks that the user exists in the same organization, is active, and has is_active=true. If null (unassigning), no lookup is required. Changing status to Resolved or Closed auto-sets sla_resolved_at to now. All updates are org-scoped; a ticket from org A cannot be updated if you belong to org B.

src/app/api/tickets/[id]/route.ts:87-160 (PATCH handler, whitelist, validation, assignee active-membership check)
What data does GET /api/tickets/[id] return?Intermediate

Returns a single ticket with full relations: contact details (name, email, role, phone), account tier and company, ticket-email associations and full email bodies, and auto-responses. Also computes and returns SLA status (whether first-response and resolution deadlines have been met, and if either is overdue) and finds up to 5 related tickets by category for the user to reference.

{
  "ticket": { id, subject, severity, status, ... },
  "sla": { first_response_ok, resolution_ok, ... },
  "similar_tickets": [...]
}
src/app/api/tickets/[id]/route.ts:8-71 (GET handler with full joins and SLA computation)

Dashboard & Aggregation

How is the dashboard query structured to avoid N+1 problems?Advanced

GET /api/dashboard kicks off the slowest queries (SLA metrics and audit-log activity) immediately as promises, rather than awaiting them sequentially. It then runs 11 independent count/fetch queries in a single Promise.all(), so they execute in parallel. After those complete, the SLA promise and metrics promise (which depends on SLA) are awaited. For the activity feed, after the activity rows are fetched, a single batched query retrieves all referenced ticket numbers and subjects at once using .in("id", ticketIds), not a loop. The response includes ticket counts (total, open, resolved today, awaiting review), breakdowns by category/severity/status, average AI confidence, SLA metrics, SLA alerts with customer names, and recent activity.

src/app/api/dashboard/route.ts:21-209 (parallel SLA, Promise.all batch, batched ticket lookups for activity enrichment)

Email Processing & Webhook Routes

How does the email polling endpoint work and why is it safe to call repeatedly?Intermediate

GET/POST /api/emails/poll (bearer-token auth, Vercel Cron) iterates over all organizations that have email_config set, calls pollNewEmails() to fetch unseen messages from IMAP, and processes each email through the pipeline. To avoid rate-limit hits on AI services, there's a 4-second delay between emails. The endpoint is idempotent: running it twice fetches the same unseen messages again and processes them again (the pipeline is responsible for detecting duplicates at a lower level). It's safe to call repeatedly because it doesn't modify state in a way that breaks if called twice.

export async function GET(req: NextRequest) {
  return handle(req);
}

export async function POST(req: NextRequest) {
  return handle(req);
}
src/app/api/emails/poll/route.ts:63-69 (GET and POST both supported for Vercel Cron flexibility); lines 11-61 (polling logic, per-email rate limiting)
What does the email queue processor do and when would it be called?Intermediate

GET/POST /api/emails/process-queue (bearer-token auth, Vercel Cron) fetches up to 50 unprocessed emails from the database (where processed=false), reprocesses them through the pipeline, and marks them as processed. This is used for retries when an email failed on first attempt, and for processing test/seed emails. Unlike poll which fetches from IMAP, this one consumes a local queue. It applies a 2-second rate limit between emails to avoid overwhelming AI services. The response includes a summary: total processed, how many succeeded/duplicated/spammed/errored.

src/app/api/emails/process-queue/route.ts:11-96 (queue processing, rate limiting, status aggregation)
What is POST /api/emails/ingest and how does it differ from poll?Intermediate

POST /api/emails/ingest (bearer-token auth) accepts incoming emails from an external email relay service. The request body contains a raw email (from_address, subject, body_text, etc.) and organization_id, and must include these required fields: from_address, subject, received_at, organization_id. The endpoint immediately processes the email through the pipeline and returns the result. Unlike poll (which iterates organizations) or process-queue (which works from a local queue), ingest is called by an external service pushing emails in real-time. It's org-scoped by the organization_id in the payload, not extracted from a session.

src/app/api/emails/ingest/route.ts:7-63

Response & FAQ Management

How does POST /api/respond work and what validation does it perform?Advanced

Sends an email reply to a customer and marks the response as sent. Requires either response_id or ticket_id, and a non-empty response_text (max 20,000 chars). It fetches the unsent auto_response record, extracts the ticket and original email, loads the org's SMTP config, sends the email via SMTP with proper In-Reply-To headers, updates the response to sent=true and stores the response_text, then auto-sets the ticket status to Resolved and backfills sla_first_response_at if it was null. All updates are org-scoped and the response query filters sent=false and organization_id before accepting the record.

if (responseText.length > 20000) {
  return NextResponse.json(
    { error: "Response text is too long" },
    { status: 400 },
  );
}
src/app/api/respond/route.ts:8-153 (POST handler, validation, email sending, ticket/response updates)
What is the request/response shape for FAQ management endpoints?Basic

GET /api/faqs returns paginated FAQs (default limit 20, max 100) for the org, supports filtering by category and full-text search in question/answer. POST /api/faqs creates a new FAQ, requires question, answer, and category fields, generates an embedding for the Q+A, and upserts the vector into Pinecone under the org's namespaced FAQ index. The response includes the created FAQ object with its id. PUT and DELETE /api/faqs/[id] are not shown in the PLAN.txt route table; check if the impl exists or note as not implemented.

Development-Only Routes

Which routes are blocked in production and why?Intermediate

Three routes check NODE_ENV and return 404 in production: DELETE /api/cleanup (deletes all tickets, emails, responses, audit logs, and Pinecone vectors; used to reset after importing junk), PATCH/POST /api/migrate (runs migrations), and POST /api/seed (seeds test data; POST /api/seed/test-emails is also dev-only). These are guarded because they're irreversible and dangerous if called in production. In development, they return normally; in production, they return a plain 404 so external callers get no hint that these endpoints exist.

export async function DELETE() {
  if (process.env.NODE_ENV === "production") {
    return NextResponse.json({ error: "Not found" }, { status: 404 });
  }
