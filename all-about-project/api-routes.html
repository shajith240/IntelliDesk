Shared conventions

What does every session-authenticated route do first?Basic
  1. requireAuth() returns the session or a 401 response.
  2. getOrgId(session) gives the caller's organization; every query filters by it.
  3. A can.* check from the policy module; failures return forbidden() (403) or notFound() (404).
  4. Path ids are validated against a UUID regex before touching the database (a malformed id is a 404, not a database error).
  5. Bodies are parsed defensively (400 "Request body must be JSON") and validated, mostly with zod .strict() schemas that reject unknown fields.

How is search text protected against PostgREST filter injection?Advanced

Supabase's .or() takes a filter string. Interpolating raw text like x%,answer.ilike.* could add conditions. Both list endpoints strip the characters filter syntax uses before interpolating.

const search = (searchParams.get("search") ?? "").replace(/[,()*%\\:"]/g, " ").trim().slice(0, 100);

Tickets & conversation

GET /api/tickets — what filters exist and how is it scoped?Intermediate

Query parameters: status (comma list, validated with isStatus), severity, category, search, assigned, page, limit, sort/order, and view=review. Agents are forced to assigned_agent = self whatever they ask for; view=review (unassigned + flagged + open) is 403 for agents. Missing SLA due dates are filled from the organization's SLA policy (org row preferred over the global default). The response includes total and total_pages.

src/app/api/tickets/route.ts:31, 102-116, 146, 185
GET /api/tickets/[id] — what does the detail contain?Intermediate

The ticket plus: contacts, accounts, teams (through the composite FK), ticket_messages with author (users) and transport (emails), auto_responses (drafts, with sent_message_id), follow_up_parent (second query), sla status, allowed_statuses read from the workflow table, and up to 5 similar tickets (agent-scoped).

src/app/api/tickets/[id]/route.ts:36-98; src/types/api.ts (TicketDetailResponse)
PATCH /api/tickets/[id] — what can be changed?Intermediate

status, severity, category (validated against fixed lists) and assigned_team_id (admin only; a foreign team is rejected by the composite FK → 400 "Invalid team"). Server-owned fields — assigned_agent, sla_first_response_at, sla_resolved_at, organization_id, ticket_number — are refused with 400. The resolution timestamp and allowed transitions are enforced by the enforce_ticket_status trigger; a check_violation with hint invalid_status_transition becomes a readable 400. Writes ticket_updated to the audit log.

src/app/api/tickets/[id]/route.ts:111-200
POST /api/tickets/[id]/messages — how do replies and notes work?Advanced

Body is a zod discriminated union: { kind: "reply", body, status_after?: "In Progress" | "Pending" | "Resolved", draft_id? } or { kind: "note", body }, body 1–20,000 characters. The caller must be able to view (else 404) and work the ticket (else 403). Notes are inserted directly (audit note_added). Replies go through sendTicketReply: 409 for a Closed ticket, a ticket with no customer address, or no connected mailbox; 400 for a disallowed status_after; 502 when SMTP rejects (the failed reply stays in the conversation as "Not delivered"). Success returns 201 with the message id, the ticket's new status, and the recipient. maxDuration = 60.

src/app/api/tickets/[id]/messages/route.ts:12-89; src/server/tickets/replies.ts
POST /api/tickets/[id]/assign — how does assignment map errors?Intermediate

Admin only. Body { assignee_id: uuid | null, note?: string ≤ 500 }. It calls the assign_ticket RPC and maps Postgres error codes: P0002 (no_data_found) → 404, 42501 (insufficient_privilege) → 403, 23514/23503 (assignee not an active admin/agent of this org) → 400.

Team, me & auth

How are members added, changed and deactivated?Intermediate

POST /api/team (admin): { name, email, role }; generates a 16-character initial password from an unambiguous alphabet (~95 bits), stores its bcrypt hash, returns it once; 409 on duplicate email; audit member_added. GET /api/team lists members; ?include=inactive is admin-only.

PATCH /api/team/[id] (admin): name, role, is_active (strict schema, at least one field). An admin can't demote or deactivate themselves, the last active admin can't be removed, and deactivating or making someone a viewer releases their open tickets through assign_ticket(…, null) with a note; audit member_updated.

src/app/api/team/route.ts:20, 48-109; src/app/api/team/[id]/route.ts:12-127
What do /api/me, /api/me/password and /api/auth/signup do?Basic
  • GET /api/me — own profile. PATCH { is_available: boolean } for admins and agents (viewers get 403: they're never assignees).
  • POST /api/me/password — current password must match (400 otherwise); new password at least 12 characters; bcrypt cost 12.
  • POST /api/auth/signup — 403 "Sign-up is closed" unless the deployment opts in; otherwise creates an organization and its first admin (409 on existing email).
src/app/api/me/route.ts:30-58; src/app/api/me/password/route.ts; src/app/api/auth/signup/route.ts:6-21
GET /api/team/workload — how are assignee candidates ranked?Basic

Admin only. Active admins and agents with a count of their open tickets (open = New/In Progress/Pending), sorted available first, then fewest open tickets, then name.

Knowledge base, search & dashboard

What happens when an admin creates, edits or deletes an article?Intermediate

POST embeds the article before saving it, so an AI failure saves nothing (503 "AI isn't set up…" or "busy"), then upserts the vector into the organization's faqs namespace. PUT re-embeds only if the question or answer changed. DELETE removes the row and its vector, so the AI stops quoting a deleted answer. GET returns each article with times_used computed as COUNT(auto_response_citations).

src/app/api/faqs/route.ts; src/app/api/faqs/[id]/route.ts; src/server/db/pinecone.ts (deleteVectors)
How do search and the dashboard respect roles?Intermediate

GET /api/search embeds the query with the workspace's AI key, queries the org's Pinecone namespaces, then hydrates results from Postgres with organization filters; agents only get their own tickets back. GET /api/dashboard computes counts by status/severity/category, SLA metrics and alerts, recent activity, "needs assignment" and "sent today" (delivered replies in ticket_messages); for agents every number is restricted to tickets assigned to them. "Today" starts at midnight in the organization's timezone.

Settings, spam & email intake

How do the mailbox and AI settings endpoints behave?Advanced

/api/settings/email-config: GET returns status only (never the secret). POST accepts Gmail { provider: "gmail", email, app_password } (16 letters, spaces ignored) or custom { provider: "imap_smtp", …, imap_port: 993, smtp_port: 465 | 587 }; custom hosts must resolve to public addresses (SSRF guard); credentials are verified by a real IMAP login and SMTP handshake, then encrypted and upserted; audit mailbox_connected. DELETE removes the row (audit mailbox_disconnected). 503 if the encryption key is missing. maxDuration = 60.

/api/settings/ai: GET returns auto_send and key status (workspace with hint/status/error, platform, or none). PATCH { auto_send } (audit ai_auto_send_changed). POST { api_key } is format-checked, verified with a free countTokens call, encrypted and saved, and emails that gave up while AI was down are requeued (audit ai_key_saved). DELETE removes the key (audit ai_key_removed).

src/app/api/settings/email-config/route.ts:19-164; src/app/api/settings/ai/route.ts
How do spam review and recovery work?Basic

GET /api/emails/spam (admin): inbound emails with is_spam from the last 30 days, newest first, max 100, each with a 200-character preview. POST /api/emails/[id]/not-spam (admin): sets is_spam = false, records who and when (not_spam_by/at), resets it into the intake queue; the pipeline then skips both spam filters for it. 404 if already recovered; audit email_marked_not_spam.

src/app/api/emails/spam/route.ts:14-29; src/app/api/emails/[id]/not-spam/route.ts:15-51
How are the machine-to-machine email routes protected and what do they return?Intermediate

poll and process-queue require Authorization: Bearer $CRON_SECRET (GET is accepted because Vercel Cron sends GET). poll ingests every connected mailbox, then drains the queue within a 50-second budget under the 60-second maxDuration, and deletes login attempts older than 30 days; it returns { intake, drain } counts. ingest requires EMAIL_INGEST_SECRET and an organization_id that must exist (400 "Unknown organization"). Missing secrets → 503.
