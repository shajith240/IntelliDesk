Interview Cheat-Sheet

The fast version: a two-minute pitch, the numbers to remember, the questions interviewers are most likely to ask with short answers, and where to find the full answer and the code on this site.

The pitch

Tell me about your project. (two minutes)Basic

"IntelliDesk is a multi-tenant, AI-assisted helpdesk for small teams. A company connects its support Gmail in one step; every email becomes a ticket, classified and prioritized by Gemini; the AI drafts replies grounded in the company's knowledge base; an admin assigns work, and agents reply from a Jira-style workspace. It's Next.js 16 on Vercel, Postgres on Supabase, Pinecone for vectors.

The parts I'm proudest of are the engineering underneath. Business rules live in the database: tenant isolation through composite foreign keys, the ticket workflow as a transitions table enforced by a trigger, and atomic functions for assignment and email intake. The schema is normalized, with derived values computed rather than stored, and 45 database checks try to break these rules. Email intake is designed for serverless: store before marking read, one idempotent commit point, a queue in a table, so a timeout never loses mail. The AI is safe by default: drafts only, strict auto-send rules, a grounding check, prompt-injection defenses and mail-loop protection. I also found and fixed real security issues, like an open database API that exposed password hashes."

Most likely questions

How do you guarantee one company can never see another's data?Advanced

Organization from the signed session, not the request; every query filtered by it; composite (id, organization_id) foreign keys so the database refuses cross-tenant references; RLS closed to browser roles; per-org vector namespaces; secrets encrypted with the org id as associated data. Tested with explicit cross-tenant attempts. → Architecture, Database Design

How did you apply normalization?Advanced

Removed a repeating group (citation id arrays → join table, 1NF), a transitive dependency (team name copied onto tickets → read through the FK, 3NF), and stored derived values (sent flags, SLA breach, usage counters). Where a derived value is worth storing, the database generates it (ai_confidence). Fixed a wrong cardinality (an email belongs to one ticket: unique FK instead of a join table). And I can explain the deliberate exceptions (JSON snapshot of the AI verdict, raw email headers). → Database Design

What happens if the server dies halfway through processing an email?Advanced

Nothing is lost or duplicated. Mail is stored before it's marked read; the ticket and first message are created by one idempotent transaction; the email is marked processed last; a retry lands on the same ticket. Queue rows are claimed with compare-and-set so overlapping runs don't collide, and a message failing 5 times is parked. → Pipeline

How do you send an email and record it atomically when SMTP isn't transactional?Advanced

Record the intent (sending), send with our own Message-ID, then record the outcome in one database transaction (complete_ticket_reply). Failures stay visible ("Not delivered"). It's the idea behind the transactional outbox, without a separate worker. → Agent walkthrough

How do you stop the AI from saying something wrong or harmful?Advanced

Drafts by default; automatic sending is opt-in and gated by rules (strong match, low-risk topic, calm customer, human sender, 2 per day); answers only from the knowledge base with an "answerable" flag; a grounding check blocks links, emails, phone numbers and amounts not in the articles; customer text passed as delimited untrusted data; JSON-schema output; no tools. → AI Design & Safety

How do you avoid infinite email loops with other auto-responders?Intermediate

Detect machine mail (RFC 3834 Auto-Submitted, Precedence, list headers, null Return-Path, system senders, our own address) and never answer it; mark our automatic replies with Auto-Submitted: auto-replied; cap automatic replies per recipient; never auto-answer a follow-up. Unit-tested. → AI Design & Safety

How is authorization designed?Intermediate

One policy module (can.*) used by every route; server-side page guards; 404 instead of 403 to avoid leaking ticket existence; critical rules repeated in the database (only active admins assign; only admins/agents can hold tickets). Defense in depth: UI hides, API refuses, database refuses. → Roles & Permissions

What security issues did you find and fix?Intermediate

The big one: an open Supabase Data API — the public anon key could read password hashes. Also a committed plaintext password, unauthenticated seed/cleanup routes, open signup, no brute-force protection, login timing leaks, non-revocable sessions, SSRF through mail hosts, SMTP without TLS, HTML and header injection in emails, filter injection in search. → Bugs & Lessons, Auth & Security

How did you change a production schema without downtime?Advanced

Expand/contract: additive migration, deploy code that uses the new shape, then a contract migration that drops the old columns. Every migration was rehearsed with all tests inside a rolled-back transaction against production first. A temporary bridge trigger covered the gap in one change. → Database Design

How did you test it?Intermediate

45 database checks that try to break each rule inside BEGIN…ROLLBACK (safe against production), 16 unit tests with Node's built-in runner on pure safety logic, typecheck/lint/build, and scripted Playwright runs per phase. Honest gap: no committed E2E suite or CI yet. → Testing

What would you do differently or next?Basic

Design invariants into the database from day one instead of retrofitting; write the rule tests first. Next: business-hours SLA with pause while Pending, password reset, notifications, branding, attachments, and CI with a committed E2E suite. → Roadmap

Why these technologies?Basic

Next.js: UI and API in one deployable with shared types. Postgres (Supabase): constraints, triggers, transactional functions — the reason the design works. Pinecone: managed vectors with namespaces for tenancy. Gemini: cheap, JSON-schema output, embeddings, free tier. GitHub Actions: a free 10-minute scheduler where Vercel's free plan allows only daily cron. Everything fits free tiers. → Decisions
