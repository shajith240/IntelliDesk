Authentication & Security

How the application authenticates users, enforces organization-scoped access, and secures webhook endpoints. NextAuth v5 with credentials provider, JWT sessions, and multi-tenant isolation via organization_id checks on every route.

Session & User Roles

What does the session object contain?Basic

After login, the session shape includes the user's id, email, name, role, organization_id, and optional avatar image. The role field is an enum: admin, agent, or viewer. All authenticated requests carry this session object through the auth() middleware.

interface Session {
  user: {
    id: string;
    email: string;
    name: string;
    role: "admin" | "agent" | "viewer";
    organization_id: string;
    image?: string | null;
  };
}
src/server/auth/config.ts:8-23 (Session interface augmentation)
How is the session created and stored?Intermediate

NextAuth v5 uses a JWT strategy with a 30-day maxAge. When a user logs in via the credentials provider (email + password verified against bcryptjs hash), the user data is returned and then encoded into a JWT token. On every request, the JWT is decoded to reconstruct the session object. The JWT callbacks enrich the token with role and organization_id, and the session callback copies those fields from the token into the session object that route handlers receive.

session: {
  strategy: "jwt",
  maxAge: 30 * 24 * 60 * 60, // 30 days
},
src/server/auth/config.ts:36-39
How is the password verified during login?Intermediate

The credentials provider queries the user by email (case-insensitive, trimmed), fetches the stored password_hash, and uses bcryptjs's compare() function to check if the plaintext password matches the hash. The hash was created when the user was invited or signed up; passwords are never stored in plaintext. If verification fails or the user is marked inactive, login returns null and the request fails.

const isValid = await compare(password, user.password_hash);
if (!isValid) {
  return null;
}

Organization Scoping & Multi-Tenancy

Why is organization_id critical to the data model?Advanced

Every row in every data table (tickets, emails, users, faqs, etc.) is tagged with an organization_id. This enforces multi-tenant isolation: an agent in Organization A cannot see, modify, or query tickets belonging to Organization B because every API route filters results with .eq("organization_id", orgId) before returning. Without this check, a malicious user could simply change the organization_id in their session token or guess other org IDs to access data they shouldn't see.

The pattern is consistent across all protected routes: extract orgId from the session, then filter the Supabase query by that organization.

src/app/api/tickets/route.ts:19-72 (org-scoped queries); src/server/auth/org-context.ts (getOrgId helper)
How does the getOrgId helper prevent accidental data leaks?Intermediate

The getOrgId() function extracts organization_id from the session and throws if it's missing. This ensures that any route using it fails hard (500 error) rather than silently proceeding without an org filter, which would be a critical security bug. Throwing is better than silently defaulting because a missing organization_id should never happen for a valid authenticated session — if it does, something is wrong and the operator should know immediately.

export function getOrgId(session: Session): string {
  const orgId = session.user?.organization_id;
  if (!orgId) {
    throw new Error("Session missing organization_id");
  }
  return orgId;
}

Webhook & Cron Authentication

Why do webhook endpoints use bearer tokens instead of session auth?Intermediate

Cron jobs and external webhooks (email ingest, email polling, queue processing) are not user-initiated requests with a logged-in session. Instead, they authenticate via a bearer token in the Authorization header, checked against a secret environment variable. This is the standard pattern for server-to-server communication. Three routes use this pattern: /api/emails/ingest (accepts emails from external service), /api/emails/poll (Vercel Cron), and /api/emails/process-queue (Vercel Cron).

src/middleware.ts:16-19 (three routes whitelisted as public-api); src/server/auth/cron.ts (verifyBearerSecret function)
How does bearer token verification prevent timing attacks?Advanced

The verifyBearerSecret() function uses Node.js's built-in timingSafeEqual to compare the incoming Authorization header against the expected secret. Regular string comparison (===) can leak information through timing side-channels: if the first byte is wrong, the comparison fails faster than if the first byte is correct but the second is wrong. The safe comparison always takes the same time regardless of which byte differs, preventing an attacker from reverse-engineering the secret one byte at a time. Importantly, the lengths are compared first—if they differ, the function returns false immediately without calling timingSafeEqual.

let isValid = false;
if (authHeader.length === expected.length) {
  try {
    isValid = timingSafeEqual(
      Buffer.from(authHeader),
      Buffer.from(expected),
    );
  } catch {
    isValid = false;
  }
}
src/server/auth/cron.ts:27-36
What happens if a webhook secret environment variable is missing?Intermediate

Instead of silently accepting all requests (dangerous) or returning a generic 401 Unauthorized, the endpoint returns 503 Endpoint is not configured. This fail-closed behavior signals that the deployment is misconfigured and must be fixed before the endpoint works. A 503 is also distinct from 401, so logs and monitoring can identify configuration errors separately from actual authentication failures.

if (!secret) {
  console.error(`${name} is not configured`);
  return NextResponse.json(
    { error: "Endpoint is not configured" },
    { status: 503 },
  );
}

Login & Route Protection

How does the login page prevent open-redirect attacks?Advanced

The login form accepts a callbackUrl query parameter to redirect users after login. However, it validates the URL with a regex before using it: /^\/[^/\\]/. This ensures the URL starts with a single forward slash, contains no backslashes, and has at least one more character after the slash, meaning it must be a relative path within the app (e.g., /dashboard) and not an external URL like https://attacker.com. If the validation fails, the default fallback is /dashboard.

const callbackUrl =
  callbackUrlParam && /^\/[^/\\]/.test(callbackUrlParam)
    ? callbackUrlParam
    : "/dashboard";
src/app/(auth)/login/page.tsx:20-23
How are dashboard routes protected from unauthenticated access?Intermediate

The Next.js middleware (at src/middleware.ts) runs on every request. For routes under /dashboard, it checks if the user has a session. If not, it redirects to /login?callbackUrl=/dashboard/..., preserving the original path so the user is sent to the right page after logging in. Auth pages (/login, /signup) are allowed for unauthenticated users; if a logged-in user tries to visit them, they're redirected to /dashboard.

src/middleware.ts:11-42
How do API routes enforce authentication?Basic

Every protected API route calls requireAuth() as the first step. This function calls NextAuth's auth() to get the session, and returns a 401 response if there's no session. After confirming authentication, routes call getOrgId() to extract and validate the organization_id, then filter all queries by that org. Webhook routes (poll, process-queue, ingest) skip this and call verifyCronRequest() instead, which checks the bearer token.

const session = await requireAuth();
if (session instanceof NextResponse) return session;
const orgId = getOrgId(session);
