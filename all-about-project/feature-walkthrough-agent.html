Agent Works a Ticket

A walk through the code an agent's browser actually exercises, end to end: login, the queue, opening a ticket, reading the conversation, drafting and sending a reply, and what happens after. Every step is traced to a real component, route, or database function.

1. Signing in and landing on My Work

Where does an agent land right after login, and why not the Command Center?Basic

The root dashboard page (/dashboard) is the Command Center, but it's gated to admin and viewer only. requirePageRole reads the session, and if the signed-in role isn't in the allowed list it redirects to that role's "home" instead of showing a 403 page. For an agent, homeFor() returns /dashboard/my-work, so an agent who opens /dashboard (or clicks a stale bookmark) is bounced straight to My Work without ever seeing the Command Center.

function homeFor(role: UserRole): string {
	return role === "agent" ? "/dashboard/my-work" : "/dashboard";
}

Where is the in-progress draft actually stored, and does it survive a page refresh?Intermediate

In window.localStorage, one key per ticket per mode (intellidesk.draft.<ticketId> for replies, intellidesk.note.<ticketId> for notes). Every keystroke writes through; if the text is edited back to the "blank" value (empty note, or the untouched AI draft) the key is removed instead of storing a no-op value. Reads and writes are wrapped in try/catch so private-mode or quota failures degrade to in-memory-only editing rather than crashing the composer. This is why closing the ticket sheet with unsent text only warns about losing focus, not the text itself — "Your reply edits stay saved on this device."

function writeStored(key: string, value: string, blank: string) {
	try {
		if (value === blank) window.localStorage.removeItem(key);
		else window.localStorage.setItem(key, value);
	} catch {
		// Best effort only — edits still work in memory for this session.
	}
}

5. Confirm and send

What does the "Review & send" confirmation dialog show, and why does it exist?Basic

Clicking "Review & send" (reply mode only — notes send immediately) opens SendConfirmDialog rather than sending straight away, since a reply emails the customer and can't be recalled. It shows the recipient, the computed subject (Re: {subject} [{ticket_number}]), the character count, the full body text, and states plainly what status the ticket will move to. Walk through the three-step protocol sendTicketReply uses to actually send the email.Advanced

SMTP can't participate in a Postgres transaction, so a reply is sent in three separate, explicitly-ordered steps: (1) insert a ticket_messages row with delivery_status: 'sending' — this records intent so a crash between steps 2 and 3 is visible as a stuck "sending" row instead of a silently lost or silently duplicated send; (2) call sendEmail with the workspace's own generated Message-ID and, when this is a threaded reply, In-Reply-To/References pointing at the most recent email in the conversation; (3) once SMTP accepts it, call the complete_ticket_reply RPC, which atomically records the outbound emails row, flips delivery_status to sent, sets first-response time, applies the requested status change (if the workflow still allows it), links the AI draft if this reply came from one, and writes the audit row.

What happens to the message row if the SMTP send itself fails?Advanced

The already-inserted ticket_messages row is updated to delivery_status: 'failed' with the trimmed provider error, the mailbox's sync-health record is updated, and a ReplyError with HTTP 502 is thrown so the composer surfaces "The email server rejected the message." 6. After sending: threading, status, availability, SLA

If the customer writes back, how does their reply attach to the same ticket?Advanced

The intake pipeline runs detectThread() against the new inbound email (matching In-Reply-To to a known Message-ID first, then a ticket-number reference, then subject+sender), and hands the result to the record_inbound_message RPC as p_thread_ticket_id. That function decides the outcome: if the matched ticket is New or In Progress, the email is just appended; if it's Pending or Resolved, it's appended and the ticket is reopened to In Progress (with an audit row); if it's Closed, a brand-new ticket is created with follow_up_of pointing at the old one instead of reopening it. A more urgent reply also raises the ticket's severity — it's never lowered by a later, calmer reply.

IF v_ticket.id IS NOT NULL AND v_ticket.status <> 'Closed' THEN
  INSERT INTO public.ticket_messages (organization_id, ticket_id, kind, author_type, email_id, body_text)
  VALUES (p_org_id, v_ticket.id, 'customer', 'customer', p_email_id, left(p_body, 100000));

  v_reopened := v_ticket.status IN ('Pending', 'Resolved');
  UPDATE public.tickets
  SET status   = CASE WHEN v_reopened THEN 'In Progress' ELSE status END,
      severity = CASE WHEN v_severity IS NOT NULL AND v_severity < severity THEN v_severity ELSE severity END
  WHERE id = v_ticket.id;

How is SLA time shown to the agent, and where does the "critical"/"warning" coloring come from?Intermediate

The sidebar's SLA section shows First response and Resolution targets, each read via readSla(): no due date means "No SLA"; a completed target compares completion time to the due time ("Met" or "Missed by <duration>"); an incomplete target counts down and buckets into critical (under 60 minutes left), warning (under 25% of the target window, or 4 hours if the window is unknown), or ok. The due dates themselves come from getTicketSLAStatus(), which maps the ticket's severity to a workspace-specific (or global default) sla_policies row.
