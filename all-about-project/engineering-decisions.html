Key Engineering Decisions & Trade-offs

Deliberate choices made while building this project, with the alternative that was rejected and why. These are the ones most likely to come up as "why did you do it this way?" follow-ups.

Architecture & organization

Why is server-only code split into src/server/ instead of living in src/lib/ with everything else?Intermediate

The codebase mixes two kinds of shared code: client-safe utilities (formatters, the API fetch wrapper, `cn()`) and server-only integrations (the Supabase service-role client, Gemini, Pinecone, IMAP/SMTP, auth config). Before the split they all lived in src/lib/, which meant nothing stopped a client component from accidentally importing the Supabase service-role key into browser code.

The fix was two-layered rather than relying on developer discipline alone:

  • Every file under src/server/ starts with import "server-only"; — a package Next.js already bundles (no install needed), which makes the build fail if that module is ever pulled into a client bundle.
  • An ESLint no-restricted-imports rule additionally blocks importing @/server/* from anything under src/components/, src/hooks/, src/lib/, or src/types/, and blocks importing @/features/* from those same shared folders.

Trade-off: this is two enforcement mechanisms for one rule (belt-and-suspenders), which is slightly redundant. The reason for both: server-only only fails at build time, after the mistake is already written; the ESLint rule catches it immediately, in the editor, before a build is even attempted.

eslint.config.mjs — no-restricted-imports patterns for @/server/* and @/features/*; every file under src/server/ (19 files) starts with import "server-only"
Why src/features/<name>/ instead of putting everything in src/components/?Intermediate

The alternative (bulletproof-react style: one flat components/ tree, or putting page-specific UI directly under app/ in private _components folders) was rejected because several components — most notably the ticket work queue — are genuinely shared across multiple routes: the Command Center embeds the same WorkQueue component that the dedicated Incoming Queue and My Work pages render standalone. A feature folder per product area (command-center, queue, ticket-workspace, knowledge-base, analytics, settings, plus auth) keeps each domain's components, hooks, and helpers together, while src/components/ui stays reserved for primitives with zero business logic.

The import-direction rule (app → features → shared) has exactly one intentional exception, documented rather than silently allowed: command-center imports queue's WorkQueue. Every other cross-feature import is disallowed.

src/features/command-center/components/command-center.tsx imports WorkQueue from @/features/queue/components/work-queue
Why no barrel index.ts re-export files anywhere in the project?Basic

Barrel files (a folder's index.ts re-exporting everything inside it) were deliberately not used, in favor of importing each module by its direct path (e.g. import { Button } from "@/components/ui/button", never from "@/components/ui"). Two concrete costs of barrels were the reason: they defeat some bundler tree-shaking because the bundler has to statically prove the rest of the barrel's exports are unused, and they're a common source of circular-import bugs once two feature folders both re-export through their own barrel and end up importing each other indirectly. With 129 source files and no barrels, every import in the project is directly traceable to the exact file that defines it.

Data & API design

Why are SLA due dates computed at read time in GET /api/tickets instead of being stored on the ticket row?Advanced

The email-processing pipeline does not persist sla_first_response_due / sla_resolution_due on every ticket at creation time. Rather than backfilling every historical row or forcing the pipeline to always know the SLA policy at ingest time, the ticket list route fetches all rows from sla_policies once per request and computes each missing due date as created_at + policy_minutes in application code before returning the list.

Trade-off accepted: this couples the read path to sla_policies lookup logic that, conceptually, belongs closer to ticket creation. The alternative — a database trigger or a backfill migration — was rejected for a project at this scale: it adds a migration and a stateful trigger to maintain, for a computation that's cheap to do per-request with a single extra query.

src/app/api/tickets/route.ts — SLA due dates are computed from sla_policies because the email pipeline does not store them on the ticket
Why does /api/dashboard start the SLA alert computation before the ticket-count queries, instead of after?Advanced

The SLA alert/metrics computation (getSLAAlerts → getSLAMetrics) is the slowest part of assembling the dashboard response, and it was originally awaited sequentially after a batch of independent count queries had already finished. The fix: kick off the SLA alerts promise and the recent- activity audit-log query immediately, in parallel with the Promise.all batch of ticket/email counts, so the slow query overlaps with the fast ones instead of stacking after them. getSLAMetrics was also changed to accept the already-fetched alerts as an optional parameter, so it doesn't refetch and recompute them a second time internally.

src/app/api/dashboard/route.ts — slaAlertsPromise / slaMetricsPromise / recentActivityPromise started before the Promise.all batch; src/server/pipeline/sla-tracker.ts — getSLAMetrics(orgId, precomputedAlerts?)
Why do the cron/webhook endpoints use a bearer secret instead of session auth, and why do they fail with 503 rather than 401 when unconfigured?Intermediate

/api/emails/poll, /api/emails/process-queue, and /api/emails/ingest are called by Vercel Cron or an external mail relay — there is no logged-in user session on those requests, so the normal requireAuth() pattern doesn't apply. Instead they check Authorization: Bearer <secret> against CRON_SECRET / EMAIL_INGEST_SECRET, compared with node:crypto's timingSafeEqual (only after confirming equal length) so the comparison isn't vulnerable to a timing side-channel.

The deliberate part: if the secret environment variable is simply unset — for example, a fresh deploy where someone forgot to configure it — the endpoint returns 503 Endpoint is not configured rather than silently accepting all requests or than returning a generic 401 that looks like "you sent the wrong secret." It fails closed, and it fails in a way that's diagnosable from the response alone.

if (!secret) {
	console.error(`${name} is not configured`);
	return NextResponse.json({ error: "Endpoint is not configured" }, { status: 503 });
}
src/server/auth/cron.ts — verifyBearerSecret() / verifyCronRequest(); timingSafeEqual import at line 3
Why does PATCH /api/tickets/[id] validate that a new assigned_agent is an active member of the caller's own organization, rather than trusting the client-supplied id?Advanced

Without this check, an authenticated agent in one organization could PATCH a ticket's assigned_agent to any user id they knew or guessed — including a user in a different organization — since the column itself has no foreign-key constraint tying it to the same org as the ticket. The route now runs a lookup (users table, filtered by id, organization_id, and is_active) before accepting the new value, and rejects with a 400 if it doesn't resolve. null (unassigning) is always allowed without the lookup.

src/app/api/tickets/[id]/route.ts — PATCH handler, assignee active-membership check before .update(updates)

UI & design

Why does the ticket queue use CSS container queries instead of viewport media-query breakpoints?Advanced

The queue table can render in more than one context with different available widths at the same viewport size — full width on its own page, or narrower next to the Command Center's sidebar. A viewport breakpoint (md:, lg:) can't tell those two cases apart, so a column set tuned for one context would overflow or look cramped in the other. Tailwind v4's container queries (@container on the wrapper, @min-[560px]: etc. on cells) size columns against the table's own rendered width instead, so the same component genuinely never produces horizontal scroll regardless of where it's mounted. Low-value columns (category, then updated-time, then customer/confidence) drop first as the container narrows, verified at 390/768/1024/1280/1440px in every place the queue is rendered.

src/features/queue/lib/grid.ts — shared ROW_GRID container-query breakpoints; src/features/queue/components/queue-list.tsx
Why a custom "AI" monogram mark instead of a sparkle/star icon for AI-generated content?Basic

Sparkle icons are used inconsistently across products to mean "AI," "favorite," "new," or "effects," with no standardized meaning to a user encountering it cold — this is a documented usability complaint (Nielsen Norman Group has written about exactly this ambiguity). The project instead uses a small custom SVG monogram (AiMark) paired with an explicit text label (AiLabel, defaulting to "AI suggestion" for analysis and "AI draft" for reply text) everywhere AI output is shown, so provenance is stated in words, not inferred from an icon.

src/components/ui/ai-mark.tsx
Why is the AI confidence indicator a 5-segment proportional meter instead of a plain percentage bar?Basic

A single continuous progress bar communicates magnitude but not a judgment about whether that magnitude is good — a reader has to know the threshold themselves. The confidence meter instead fills a fixed 5-segment bar in proportion to the score and colors the fill by band (green ≥85%, blue ≥70%, amber ≥50%, red below), with the same band function driving both the meter and any nearby text label, so the color and the words never disagree with each other.

src/components/ui/confidence-meter.tsx — confidenceBand() shared by ConfidenceMeter and the ticket workspace's "High/Moderate/Low confidence" text
Why is the login page's animated gradient built in pure CSS instead of a canvas/WebGL shader or an animation library?Intermediate

The brief was a slowly drifting, grainy blue gradient with no new npm dependencies. The implementation uses three oversized, blurred radial-gradient elements animated purely on transform (translate/ rotate/scale) via CSS keyframes — transform is GPU-composited and doesn't trigger layout or paint on every frame, unlike animating background-position or gradient stops directly would. The grain texture is a single inline SVG data URI using feTurbulence (fractal noise) plus a feColorMatrix to push it toward white/transparent, tiled with mix-blend-mode: overlay. The whole thing collapses to a static gradient under the existing global prefers-reduced-motion rule with no extra code, since that rule already zeroes out animation durations project-wide.

src/app/globals.css — .grain-field / .grain-noise / id-drift-a/b/c keyframes; src/features/auth/components/auth-hero.tsx

Repository structure

Why does the app live at the repository root instead of in a subfolder?Basic

The app previously lived in an intellidesk-frontend/ subfolder inside the repo. It was moved to the repo root because Vercel's default "Root Directory" setting is the repo root — leaving the app in a subfolder means every teammate and every deploy configuration has to know and set that non-default path. The move was scripted rather than done by hand: a script resolved every relative and @/-alias import in the old tree to a concrete file before moving anything, then re-emitted each import path against the new location, so nothing could be left pointing at a file that had silently moved out from under it.
