Data Model & Schema

The live schema in public, as it exists after all 13 migrations (supabase/migrations/001…013). It is the composition of an "expand" migration and a later "contract" migration for the assignment model (007→013), the conversation model (009→013), and the normalization pass (012→013) — a column documented here may have been added by one migration and reshaped or dropped by a later one; each table section says which. For the reasoning behind the normalization itself, see Database Design & Migrations.

How the schema hangs together

What does the schema look like at a glance?Basic

Every tenant-owned table hangs off organizations through an organization_id column (added table-by-table in migration 002, made NOT NULL for the core tables in 007). The two entities with their own multi-row histories are tickets (customer-facing work items) and emails (the raw transport log, both directions since 009). A ticket's conversation — customer messages, agent/AI replies, and internal notes — lives in ticket_messages, one row per turn, each optionally pointing at the raw emails row it was sent or received as.

Why do so many foreign keys reference a composite (id, organization_id) instead of just id?Advanced

A plain ticket_id UUID REFERENCES tickets(id) only guarantees the ticket exists — nothing stops a row from pointing at a ticket in a different organization. Migration 007 adds UNIQUE (id, organization_id) on the parent tables (users, teams, tickets, accounts, emails) and then has every child's foreign key reference that composite: FOREIGN KEY (ticket_id, organization_id) REFERENCES tickets (id, organization_id). If the child row's organization_id doesn't match the parent's, Postgres rejects the insert — cross-tenant links become physically impossible instead of relying on every query remembering to filter by org.

What does ON DELETE SET NULL (column) mean — isn't SET NULL a plain clause?Advanced

For a composite foreign key, Postgres 15+ lets ON DELETE SET NULL take a column list so only the referencing column is nulled, not every column in the key. Without the column list, ON DELETE SET NULL on (assigned_agent, organization_id) would null out organization_id too when the user is deleted — which would break every other constraint on that row. ON DELETE SET NULL (assigned_agent) nulls only assigned_agent and leaves organization_id intact.

Why keep both is_active and is_available on users?Intermediate

They answer different questions. is_active is an admin decision: can this person sign in and hold tickets at all (a deactivated account also has its open tickets released, see PATCH /api/team/[id]). is_available is a self-service toggle an agent flips (PATCH /api/me) to say "don't route new work to me right now" without losing account access or existing tickets. enforce_ticket_assignee() only checks is_active and role when assigning — availability just changes sort order in the assignee-candidate list.

Why did the global contacts.email UNIQUE and users.email UNIQUE constraints need to change?Intermediate

A single global UNIQUE on contacts.email meant one person's address could only ever be a contact for one workspace across the whole deployment — impossible once multiple tenants can share this product. Migration 012 drops contacts_email_key in favor of the per-organization index from 007 (contacts_org_email_key on (organization_id, lower(email))). For users, the case-sensitive global unique was simply redundant once the case-insensitive users_email_lower_key existed (007), so 012 drops the older one — login is still one account per email across the whole deployment, which is correct because a user account (unlike a contact) belongs to exactly one workspace.

Why is ai_confidence a generated column instead of a plain one the pipeline writes?Advanced

Before 013, the pipeline wrote confidence twice: once inside ai_classification (the full verdict object) and once flattened into its own ai_confidence column so it could be indexed/averaged cheaply. Two copies of the same fact can drift if one write path forgets the other. 013 drops the stored column and replaces it with GENERATED ALWAYS AS ((ai_classification->>'confidence')::real) STORED: Postgres computes and stores it automatically from ai_classification on every write, so it's still an indexable/averageable real column (used by /api/dashboard's avg_ai_confidence), but it is now physically impossible for it to disagree with the JSON it's derived from — you cannot UPDATE tickets SET ai_confidence = ... directly; Postgres rejects writes to a generated column.

What enforces that a ticket can't skip straight from New to some invalid status?Intermediate

The enforce_ticket_status() trigger function, BEFORE INSERT OR UPDATE OF status on tickets. On an update where the status actually changes, it checks the pair exists in ticket_status_transitions and raises check_violation with hint invalid_status_transition if not — which PATCH /api/tickets/[id] catches by Postgres error code and turns into a 400. The same function also owns sla_resolved_at: clears it when the new status is open, sets it (or preserves it on Resolved→Closed) when the new status is closed.

  RAISE EXCEPTION 'Ticket % cannot move from % to %', OLD.ticket_number, OLD.status, NEW.status
    USING ERRCODE = 'check_violation', HINT = 'invalid_status_transition';
END IF;

Why did ticket numbering move from one global sequence to a counter row per organization?Intermediate

The original schema (001) had a single ticket_number_seq shared by every tenant. Because ticket numbers are visible to customers, two workspaces could compare notes and infer each other's ticket volume from the gaps (TKT-00031 then TKT-00087 means roughly 55 tickets happened elsewhere in between). Migration 012 replaces the sequence with one ticket_counters row per organization and an upsert-based generate_ticket_number(): the row lock on that single counter row serializes concurrent inserts for one organization without blocking any other organization's inserts.

What does the ticket_messages_kind_shape CHECK actually enforce?Advanced

It ties three columns together per kind so an inconsistent row is impossible: a customer message must have author_type='customer' and no delivery status (it was never sent by this app); a reply must have author_type agent or ai and a delivery status (it always goes through SMTP); a note must have author_type='agent', no delivery status, and no linked email (it's never emailed).

CONSTRAINT ticket_messages_kind_shape CHECK (
     (kind = 'customer' AND author_type = 'customer' AND delivery_status IS NULL)
  OR (kind = 'reply'    AND author_type IN ('agent', 'ai') AND delivery_status IS NOT NULL)
  OR (kind = 'note'     AND author_type = 'agent' AND delivery_status IS NULL AND email_id IS NULL)

supabase/migrations/009_conversation_model.sql:161-165
How is a reply recorded atomically given that sending an email can't be part of a database transaction?Advanced

sendTicketReply() splits the operation into three steps so a crash between them is visible instead of silently inconsistent: (1) insert a ticket_messages row with delivery_status='sending' — this is the only step before the network call, so it commits even if SMTP never answers; (2) call SMTP; (3) on success, call complete_ticket_reply(), which in one transaction inserts the outbound emails row, flips the message to 'sent' and links its email_id, sets sla_first_response_at if this is the first reply, applies the requested status transition (re-validated against ticket_status_transitions), links the AI draft via sent_message_id if one was used, and writes the reply_sent audit row. A message stuck in 'sending' is the visible symptom of a crash between steps 2 and 3.

How is audit_logs actually made append-only — isn't that just a comment/convention?Advanced

It's enforced by a trigger, not a convention. protect_audit_log() runs BEFORE UPDATE OR DELETE and raises insufficient_privilege unless the session has set intellidesk.audit_maintenance = 'on' for the current transaction — which no application code does; it's reserved for deliberate manual maintenance. The one exception it allows even without that flag: when a referenced user or ticket is deleted, the FK's ON DELETE SET NULL nulls actor_user_id or ticket_id on the audit row, and the trigger recognizes that specific shape of change (old row equal to new row except for one of those two columns going to NULL) and lets it through without requiring the flag.

IF current_setting('intellidesk.audit_maintenance', true) IS DISTINCT FROM 'on' THEN
  RAISE EXCEPTION 'audit_logs is append-only (% refused)', TG_OP
    USING ERRCODE = 'insufficient_privilege';
END IF;

Walk through what record_inbound_message() does with a reply to a Closed ticket.Advanced

First it checks idempotency: if a ticket_messages row already references this email_id (the column is UNIQUE), it returns the existing ticket immediately — safe to call twice for the same email. Otherwise, if the thread detector matched a ticket and that ticket's status is not Closed, the email is appended as a new customer message; if the ticket was Pending or Resolved it's reopened to In Progress and a more urgent severity on the reply wins (compared as text, since 'P1' < 'P2' lexically). But if the matched ticket is Closed, that branch is skipped and it falls through to creating a brand-new ticket with follow_up_of set to the old ticket's id — a Closed ticket never receives new messages directly; a reply to it always starts a fresh, linked ticket.

IF v_ticket.id IS NOT NULL AND v_ticket.status <> 'Closed' THEN
  INSERT INTO public.ticket_messages (...) VALUES (...);
  v_reopened := v_ticket.status IN ('Pending', 'Resolved');
  ...
  RETURN QUERY SELECT v_ticket.id, v_ticket.ticket_number, false, v_reopened;
  RETURN;
END IF;
-- New ticket, or a follow-up to a Closed one.
IF v_ticket.id IS NOT NULL THEN
  v_follow_up := v_ticket.id;
END IF;

Where does row locking (FOR UPDATE) matter in these functions, and why?Advanced

Three functions lock a row before mutating it: assign_ticket() locks the ticket (SELECT ... FOR UPDATE) before comparing/changing assigned_agent, so two concurrent assignment requests for the same ticket serialize instead of racing; complete_ticket_reply() locks both the message and the ticket before updating them, since it's finishing a reply that another concurrent request must not also try to complete; record_inbound_message() locks the matched ticket before appending to it or deciding to reopen it, so two inbound emails to the same ticket arriving close together don't both read a stale status. All three run inside implicit function-level transactions (PL/pgSQL functions are transactional by default when called outside an explicit transaction block), so the lock plus the writes plus the audit insert commit or roll back together.

Row-level security and the archive schema

RLS is enabled everywhere, but by policy, not by role separation Migration 006 enables row-level security on every table in public and leaves zero policies on any of them — the default-deny behavior means anon and authenticated (the PostgREST-facing roles) see nothing, even if a stray GRANT were re-added by mistake later. The application itself never uses those roles: it talks to Postgres exclusively with the service_role key from the server (src/server/db/supabase.ts), which has BYPASSRLS. Multi-tenant isolation is therefore enforced entirely by every route filtering on organization_id and by the composite foreign keys described above — not by RLS policies, which migration 003's earlier (superseded) per-table policies had attempted. supabase/migrations/006_lockdown_public_api.sql:1-73
What is the archive schema and is anything still using it?Basic

Migration 006 moves two legacy prototype tables — tickets_old and customers_old — out of public and into a new archive schema that PostgREST does not expose, rather than dropping them outright. All privileges on that schema are revoked from PUBLIC, anon, and authenticated. Nothing in the application code read for this page (the 24 API routes, the server modules) queries archive.*; PLAN.txt's ground truth confirms these two tables as "Archived… not used."

CREATE SCHEMA IF NOT EXISTS archive;
REVOKE ALL ON SCHEMA archive FROM PUBLIC, anon, authenticated;
ALTER TABLE IF EXISTS public.tickets_old SET SCHEMA archive;
ALTER TABLE IF EXISTS public.customers_old SET SCHEMA archive;
REVOKE ALL ON ALL TABLES IN SCHEMA archive FROM PUBLIC, anon, authenticated;
