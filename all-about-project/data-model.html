Data Model & Database Schema

PostgreSQL via Supabase. Twelve tables connected by organization-scoped foreign keys, with row-level security as a defense-in-depth layer, and a single service-role connection from the app to the database. Migrations are numbered, stable, and applied in order.

Table structure & relationships

What are the 12 tables and how are they related?Intermediate

The database is organized around organizations and their membership:

  • organizations — top-level tenant. Each org has a name, slug (unique URL-safe id), domain, plan, and max_agents.
  • users — belong to one organization. Schema: id, organization_id (FK), email, name, password_hash, role (admin/agent/viewer), is_active, created_at, updated_at.
  • accounts — customer companies. Scoped to org. Schema: id, domain, company_name, tier (Gold/Silver/Bronze), csm_name/email, plan, location.
  • contacts — individual customers tied to accounts. Schema: id, account_id (FK), email, name, role, department, phone, is_lead, lead_status.
  • teams — support teams within an org. Schema: id, organization_id (FK), name, description, category_routing (array of categories).
  • tickets — the main entity. Belong to org, account, and contact. Schema includes status, category, severity (P1-P4), ai_confidence, summary, assigned_agent, assigned_team, SLA timestamps.
  • emails — individual messages. Scoped to org. Schema: message_id, from_address, to_address, subject, body_text, body_html, received_at, processed, is_spam, language, embedding_id.
  • ticket_emails — join table linking tickets to emails. Schema: ticket_id (FK), email_id (FK), relationship (original/reply/forward/duplicate).
  • sla_policies — global defaults, not org-scoped. Four rows: one per severity (P1-P4), each with first_response_minutes and resolution_minutes.
  • faqs — knowledge base articles, scoped to org. Schema: question, answer, category, solution_steps (array), video_url, success_rate, times_used, embedding_id.
  • auto_responses — candidate replies generated by the pipeline, scoped to org. Schema: ticket_id (FK), email_id (FK), response_text, match_type (perfect/partial/none), match_score, cited_faq_ids, sent, sent_at.
  • audit_logs — append-only history, scoped to org. Schema: ticket_id (FK), action, details (JSONB), performed_by, created_at.

  sla_resolved_at TIMESTAMPTZ,
  sla_breach BOOLEAN DEFAULT FALSE,
  escalation_count INT DEFAULT 0,
  auto_response_sent BOOLEAN DEFAULT FALSE,
  auto_response_type TEXT CHECK (auto_response_type IN ('perfect', 'partial', 'none')),
  is_flagged_for_review BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

Multi-tenancy & access control

How does the app prevent one organization's data from leaking to another?Intermediate

The primary control is in application code: every query that touches organization data calls requireAuth() to verify the session, then getOrgId(session) to extract the user's org, then filters with .eq("organization_id", orgId). This pattern is enforced across all routes; there is no unscoped read path.

Row-level security provides a second layer but is not the primary control. The app uses the Supabase service-role key, which bypasses RLS entirely. RLS policies exist to defend against accidents: if a developer forgets the org-scoping filter, the database itself stops the leak. The policies are defined so that even if an anon or user key were used (unlikely with the current auth model), RLS would enforce org membership.

src/app/api/tickets/route.ts lines 15-72 show the requireAuth() → getOrgId() → .eq("organization_id", orgId) pattern; supabase/migrations/003_rls.sql lines 19-21 state: "The application uses supabase service_role key which BYPASSES RLS. These policies are defense-in-depth for any future use of anon/user keys."; README.md "Security notes" confirms this architecture
Where are the IMAP/SMTP mailbox credentials stored, and how are they accessed?Intermediate

Each organization can configure up to one IMAP/SMTP mailbox from the Settings page. The credentials are stored in a JSONB column email_config on the organizations table with the structure: { "imap": { "host": "...", "port": 993, "user": "...", "pass": "..." }, "smtp": { "host": "...", "port": 587, "user": "...", "pass": "..." } }. These are server-only secrets — they're fetched by the email pipeline (on cron) and the settings page (for admin viewing), both of which run only server-side. There's no equivalent to this data in the browser.

supabase/migrations/004_email_config.sql defines the email_config JSONB column on organizations with the exact structure documented; README.md lines 107-108 document that "Mailbox credentials (IMAP/SMTP) are configured per organization from the app's Settings page, not from environment variables; they are stored in Supabase."

Indexes, triggers, and constraints

How is the ticket_number generated, and what ensures it's always unique?Basic

Ticket numbers are auto-generated before insert by a PostgreSQL trigger. The sequence ticket_number_seq starts at 1 and increments on each new ticket. A trigger function formats it as 'TKT-' || LPAD(nextval('ticket_number_seq')::TEXT, 5, '0'), producing TKT-00001, TKT-00002, etc. The ticket_number column has a UNIQUE constraint, so if two tickets somehow tried to insert the same number, the database would reject the second. A second trigger updates the updated_at timestamp on every write.

supabase/migrations/001_initial_schema.sql lines 165-180 define the ticket_number_seq sequence and the generate_ticket_number() trigger; lines 191-194 define the set_updated_at trigger
What indexes exist on the tables and why?Intermediate

Indexes are added on frequently filtered columns. For example:

  • idx_tickets_org on tickets(organization_id) — every query filters to one org.
  • idx_tickets_status on tickets(status) — the ticket list is filtered by status.
  • idx_tickets_severity on tickets(severity) — SLA alert computation groups by severity.
  • idx_emails_processed on emails(processed) — the email pipeline looks for unprocessed messages.
  • idx_contacts_email on contacts(email) — customer deduplication looks up existing contacts by email.
  • idx_users_org on users(organization_id) — team member listings are org-scoped.

No composite indexes or partial indexes are used; all are simple B-tree indexes on a single column.

supabase/migrations/001_initial_schema.sql and 002_auth.sql define all indexes; they follow a naming pattern idx_<table>_<column>
Are there foreign-key constraints between all related tables?Intermediate

Most critical relationships have foreign keys with ON DELETE CASCADE or ON DELETE SET NULL. For example, ticket_id UUID REFERENCES tickets(id) ON DELETE CASCADE means if a ticket is deleted, all its related ticket_emails and auto_responses are deleted too. However, assigned_agent TEXT on tickets is just a TEXT column, not a foreign key to users — so the application code is responsible for validating that the assigned agent belongs to the same organization. This is why the API route for updating an assignee checks org membership before accepting the assignment.

supabase/migrations/001_initial_schema.sql shows ticket_emails with ON DELETE CASCADE (line 115); auto_responses with ON DELETE CASCADE (line 142); src/app/api/tickets/[id]/route.ts validates assigned agent membership in the PATCH handler before allowing the update

TypeScript types & API responses

How do the TypeScript type definitions mirror the database schema?Basic

Every table has a corresponding TypeScript interface in src/types/index.ts. For instance, the Ticket interface has fields that match the table columns: id, ticket_number, status, severity, ai_confidence, subject, summary, plus joinable fields like account?: Account and emails?: TicketEmail[] that reflect the foreign keys. Enums like TicketStatus and Severity map to the CHECK constraints in SQL (e.g., status IN ('New', 'In Progress', 'Resolved', 'Closed')).

src/types/index.ts defines Organization (lines 37-46), User (lines 48-61), Ticket (lines 113-143), and the other 9 entities; each maps to a table in the schema; Enums like TicketStatus (line 8) and Severity (line 10) match SQL CHECK constraints
What does an API response for a ticket list look like?Basic

The GET /api/tickets response is a TicketListResponse object with: { tickets: TicketListItem[], total: number, page: number, limit: number, total_pages: number }. Each TicketListItem is a Ticket with the account and contact joined in, and optional fields like email threads. The response is paginated; by default it returns 20 per page, with a maximum of 100. The client can sort by created_at, updated_at, severity, or status, and can filter by status, severity, category, assigned agent, and search terms.

src/types/api.ts lines 38-44 define TicketListResponse; TicketListItem is defined at lines 33-36; src/app/api/tickets/route.ts implements the sorting, filtering, and pagination logic
