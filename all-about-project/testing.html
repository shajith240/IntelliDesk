Testing Strategy

How this project verifies correctness in the absence of automated tests. The project uses TypeScript strict mode, ESLint architectural boundaries, and build-time checks instead. This section also covers where a test suite would provide the most value if one were added.

Current verification approach

Not implemented — There are no automated unit, integration, or end-to-end tests in this project. Verification relies on static analysis and the build process.
What mechanisms catch bugs before they reach production?Basic

The project uses a defense-in-depth approach without automated runtime tests:

  • TypeScript strict mode catches type mismatches at build time, preventing entire classes of runtime errors (accessing undefined properties, type guards, null coercion).
  • ESLint's no-restricted-imports rule prevents architectural violations at lint time: server-only modules cannot be imported into browser code, and feature code cannot import from shared utilities.
  • server-only package makes the build fail if a server-only file is accidentally bundled for the browser.
  • npm run build (Next.js production build) catches dead code, unreachable branches, and initialization errors before deployment.
  • npm run lint (ESLint) runs on every commit in CI/CD and catches import violations, unused variables, and style issues.

How does ESLint's no-restricted-imports rule enforce architecture?Intermediate

The ESLint config defines two import boundaries to prevent accidental architectural violations:

files: ["src/components/**", "src/hooks/**", "src/lib/**", "src/types/**"],
rules: { "no-restricted-imports": ["error", { patterns: [
  { group: ["@/server", "@/server/*"], message: "Server-only module..." },
  { group: ["@/features", "@/features/*"], message: "Shared code must not depend on a feature..." }
] }] }

If a client component tries to import { supabaseAdmin } from "@/server/db/supabase", lint fails immediately with a clear error message, before the code is even built. This catches the mistake in the editor in real time.

Does the build catch runtime errors in server code, even without tests?Intermediate

Yes, partially. TypeScript strict mode and the Next.js build process catch many errors before production:

  • Type mismatches on API route parameters and responses (the type system prevents passing the wrong shape to a database query).
  • Calling a method that doesn't exist on an object (e.g., supabaseAdmin.from('tickets').slct() fails at build time because slct is not a valid method).
  • Missing environment variables are caught when the route first runs, not at build time, but the error message is clear and the app fails fast.
  • Logic errors (e.g., an off-by-one error in SLA calculations) are not caught without a test or manual verification; the code compiles and runs.

Manual verification in practice

How is new functionality verified before it ships?Basic

Changes are verified through manual testing in the development and staging environments:

  • Local npm run dev runs the full app for manual exploration before any commit.
  • The build pipeline (npm run lint && npm run build) must pass for any pull request.
  • Integration testing is manual: standing up a full test org with sample IMAP mailbox credentials, sending test emails, and verifying the end-to-end pipeline (ingest → classify → draft → reply).
  • Data accuracy (SLA calculations, AI confidence scores, ticket sorting) is verified by hand against expected outputs.

The README notes this explicitly: "No automated test suite exists yet; verification is npm run lint and npm run build, plus manual QA."

What is the cost of missing automated tests for this codebase?Intermediate

The risk is concentrated in a few high-impact areas:

  • Email pipeline logic (IMAP polling, spam detection, thread matching) is complex and stateful; a regression here could silently drop emails or misclassify threads. Current verification is manual with sample mailboxes.
  • SLA calculations and date arithmetic using the date-fns library are easy to get wrong (off-by-one, timezone mishandling); a change to readSla() could silently cause incorrect breach predictions.
  • Database queries and org-scoping: every API route filters by organization_id, and a missing filter would silently leak data between organizations. This is caught at code review and by type checking, but not by automated tests.
  • API response shapes are documented in the README but not validated by the client; a backend route that returns the wrong shape could silently break the UI.

None of these have caused production incidents in the current project lifetime, suggesting that manual review and the build-time checks are sufficient for the team's velocity and project scope. A test suite would reduce regression risk and allow faster iteration.

Recommendations: adding tests

If you were to add a test suite, where would you start?Advanced

Start with the SLA calculation logic, which is pure, deterministic, and easy to test. The readSla() function in src/lib/ticket-meta.ts takes a due date, a completion timestamp, and a current time, and returns the tone/label without side effects:

export function readSla(
  dueIso: string | null | undefined,
  completedAt: string | null | undefined,
  now: Date,
  windowMinutes?: number,
): SlaReading {
  if (!dueIso) return { tone: "none", label: "No SLA", minutesRemaining: null };
  const due = parseISO(dueIso);
  if (completedAt) {
    const done = parseISO(completedAt);
    return done <= due
      ? { tone: "met", label: "Met", minutesRemaining: null }
      : { tone: "breached", label: `Missed by ${formatDuration(differenceInMinutes(done, due))}`, minutesRemaining: null };
  }
  const remaining = differenceInMinutes(due, now);
  if (remaining < 0) {
    return { tone: "breached", label: `Breached ${formatDuration(-remaining)} ago`, minutesRemaining: remaining };
  }
  const warnAt = windowMinutes ? windowMinutes * 0.25 : 240;
  const tone: SlaTone = remaining < 60 ? "critical" : remaining < warnAt ? "warning" : "ok";
  return { tone, label: `${formatDuration(remaining)} left`, minutesRemaining: remaining };
}

This function is a perfect candidate for unit tests: pass in a due date in the past with no completion time and verify the "breached" tone is returned. Cover edge cases like midnight crossings, the 25% warning threshold, and the special "critical" mode below 60 minutes. These tests would run in milliseconds and be stable (no flaky clock dependencies once you freeze the "now" parameter).

What other parts of the codebase would benefit most from unit tests?Advanced

In order of impact and ease:

  • Email parser utility functions (src/server/email/parser.ts): isLikelySpam(), extractSignature(), cleanEmailBody(), and normalizeSubject() are deterministic and have many edge cases (HTML entities, quoted reply markers, signature patterns). Unit tests would catch regressions in spam filtering and body cleaning instantly.
  • Formatters in ticket-meta.ts: formatDuration(), formatDateTime(), and confidencePercent() take simple inputs and produce strings; tests would verify they handle boundary cases (0 minutes, null values, NaN).
  • API route integration tests (harder): spin up a test database, create a test org, call GET /api/tickets, and verify the response shape and SLA values. These would catch regressions in data shape but would require a test database and more setup.
  • Email pipeline end-to-end tests (hardest): ingest a raw email, verify it's parsed correctly, classified, and stored with the right SLA dates. This would require a full Supabase/Gemini/Pinecone test harness and would be slow, but it would catch subtle regressions in the core feature.
Should this project prioritize unit tests or end-to-end tests?Intermediate

Start with unit tests for pure utilities, then add E2E tests for the email pipeline.

Unit tests for utility functions (SLA calc, email parsing, formatters) are fast, stable, and catch regressions instantly. They're also low friction to add — just import the function, call it with test data, and assert the output.

End-to-end tests are slower and require a test database, but they're essential for the email pipeline because the logic is complex and involves multiple services (IMAP, Supabase, Gemini, Pinecone). An E2E test that verifies "email arrives → ticket created with correct SLA due date → AI draft generated" would catch whole-system regressions that unit tests alone can't catch. However, E2E tests would run in seconds, not milliseconds, so run them less frequently (per PR, not per save).

A pragmatic plan: write unit tests for the utility functions in the next sprint, add E2E smoke tests for the pipeline in the sprint after, and gradually expand both as confidence grows.
