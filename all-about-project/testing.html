Database tests

How can tests run against the live production database safely?Advanced

Each suite is one BEGIN; DO $$ … $$; ROLLBACK; script. The DO block creates its own fixtures (users, tickets, emails) inside the transaction, attempts the forbidden operation inside a nested BEGIN … EXCEPTION WHEN <error> block, and raises if the database did not refuse. Every check prints PASS …; the first failure aborts. The final ROLLBACK discards everything, so nothing touches real data. Running against production is deliberate: it tests the real schema and the real data (e.g. that the backfills left no gaps).

ok := false; BEGIN UPDATE audit_logs SET action = 'tampered' WHERE ticket_id = t; EXCEPTION WHEN insufficient_privilege THEN ok := true; END;
IF NOT ok THEN RAISE EXCEPTION 'FAIL 5a: audit row edited'; END IF;

How were the tests used when writing migrations?Advanced

Every migration was rehearsed before being applied: the migration body plus every suite ran in a single rolled-back transaction against production. This caught real problems before they reached the live database: an existing constraint name colliding in 007, Postgres refusing ON DELETE SET NULL on a foreign key with a generated column in 009, unique keys that had to exist before the table referencing them in 012, and a test whose setup the new trigger (correctly) overrode. After applying, the suites ran again against the live schema.

Why Node's built-in test runner instead of Jest or Vitest?Intermediate

Node 22+ runs TypeScript directly (type stripping) and ships node:test and node:assert, so there is no test dependency, config or transpiler to maintain. The script disables one warning about module type detection:

"test": "node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON --test tests/unit/"
package.json

The trade-off: the tested modules must be importable without Next.js. So the unit-tested code is written as pure modules with no I/O and no server-only import (automated.ts, grounding.ts, time-zone.ts, email-domains.ts), and imports use explicit .ts paths, allowed by allowImportingTsExtensions in tsconfig. Keeping decision logic pure and I/O at the edges is good design anyway.

Did the tests catch real bugs?Intermediate

Yes. The bounce test failed on its first run: mailparser parses Content-Type into { value, params }, so reading only value lost report-type=delivery-status and delivery reports weren't recognised. The detector now inspects the whole header object.

End-to-end verification

How was end-to-end behaviour verified?Intermediate

For each phase, a Playwright script (headless Chromium) ran against a local production build (npm run build, AUTH_TRUST_HOST=true npm start) connected to the real database. Scripts created temporary admin/agent/viewer accounts, exercised APIs and UI, took screenshots, and then cleaned up every row they created (using the audit-maintenance flag where needed). Examples of what was checked: agents only see their tickets and get 404 for others; nobody but an admin can assign; viewers can't write; deactivation releases tickets and blocks login; the sixth failed login is throttled; signup is closed; notes and replies obey roles; invalid status changes return readable errors; a rejected AI key saves nothing; spam recovery requeues the email; without an AI key email waits in the queue instead of becoming a ticket.

Not committed These scripts lived in a scratch directory and are not part of the repository or CI. Turning them into a committed Playwright suite is on the roadmap.
What isn't tested?Basic
Gaps
  • No committed end-to-end suite and no CI workflow that runs tests on every push.
  • Route handlers have no automated tests (verified by the scripted runs only).
  • Real sending and threading through Gmail wasn't exercised end to end in production (no mailbox was connected at the time).
  • No load or concurrency tests beyond the database-level locking guarantees.
  • AI output quality isn't measured.
