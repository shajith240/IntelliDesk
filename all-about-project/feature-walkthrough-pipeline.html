Email → Ticket → AI Draft: End-to-End Pipeline

Trace a single incoming customer email through the entire processing pipeline: from ingestion, spam detection, and deduplication, through AI classification and ticket creation, to draft response generation. Understand what database tables are written in what order, and which decisions determine whether a ticket is auto-classified or flagged for human review.

Step 1: Email Ingestion (Webhook or Cron)

How does an email enter the system—via webhook or cron?Basic

Two entry points exist, both secured by bearer-secret authentication rather than session auth. POST /api/emails/ingest is a webhook endpoint called directly by an external email relay service; GET/POST /api/emails/poll is a Vercel Cron endpoint that pulls new messages from IMAP on a schedule for each organization that has email configured. Both routes call processEmail() from the processor pipeline. Ingest fails closed with 503 if the secret environment variable is unset; poll silently skips orgs without IMAP credentials rather than erroring.

Four fields must be present: from_address, subject, received_at, and organization_id. All other fields (message_id, from_name, to_address, cc, body_text, body_html, etc.) are optional and default to empty string or null. The route validates required fields and rejects with 400 if any are missing.

Step 2–5: Pipeline Orchestration and AI Classification

What is the exact sequence of operations inside the email processor?Advanced

The processor runs 11 sequential steps in this order: (0) clean email body, (1) quick spam check by pattern/regex, (2) generate embedding, (3) check for duplicates, (4) detect thread (reply-to/in-reply-to), (5) AI classification by Gemini, (5b) skip ticket if AI flags as spam, (6) customer identification, (7) save email to DB, (8) store embedding in Pinecone, (9) create or update ticket, (10) generate and conditionally send auto-response, (11) audit log. If any step fails, an error response is returned and the failed email is saved for retry.

Step 3: Deduplication

How does the system detect duplicate emails?Intermediate

Two methods are used in order: first, an exact Message-ID lookup (if the incoming email has one and a non-spam prior email with the same Message-ID already exists in Pinecone, it's a duplicate). Second, semantic similarity search via Pinecone: if the embedding matches another email from the same sender within the last 72 hours with a similarity score ≥ 0.85, it's flagged as a duplicate. If either check matches, the result includes the duplicate_of ID and similarity score.

const DEDUP_SIMILARITY_THRESHOLD = 0.85;
const DEDUP_TIME_WINDOW_HOURS = 72;

export async function checkDuplicate(messageId: string | null, fromAddress: string,
	embedding: number[], receivedAt: Date, orgId: string): Promise {
	// 1. Exact message-id match
	if (messageId) {
		const { data: existing } = await supabaseAdmin.from("emails")
			.select("id, is_spam").eq("message_id", messageId)
			.eq("organization_id", orgId).single();
		if (existing && !existing.is_spam) {
			return { is_duplicate: true, similarity_score: 1.0, method: "message_id" };
		}
	}
	// 2. Semantic similarity
	const results = await queryVectors(orgNamespace(orgId, "emails"), embedding, 5,
		{ from_address: fromAddress, timestamp: { $gte: cutoffTimestamp } });
	if (results && results[0]?.score >= DEDUP_SIMILARITY_THRESHOLD) {
		return { is_duplicate: true, similarity_score: results[0].score, method: "semantic" };
	}
	return { is_duplicate: false, ... };

Step 4: Customer Identification

How does the system identify which customer account an email belongs to?Intermediate

The system tries three strategies in order, each creating a contact/account if needed: (1) exact email match in existing contacts for this org, (2) domain match against existing accounts (if email domain matches an account's domain, create a new contact under that account), (3) new lead (extract name and company from email signature, create both account and contact as Bronze tier). The result includes contact_id, account_id, account_name, account_tier, and the method used.

Step 5: AI Classification

What does the Gemini classification prompt return, and how is it parsed?Intermediate

The classification prompt sends the email (from, subject, body) to Gemini and asks for a JSON object with these fields: is_spam (boolean), category (one of 9 predefined values like "Technical Support", "Billing/Invoice", etc.), severity (P1–P4), language (english/hindi/mixed/other), sentiment (positive/neutral/negative/angry), confidence (0–1), summary (1–2 sentences), key_entities (array), suggested_tags (array), requires_human_review (boolean), and reasoning (brief explanation). The response is parsed as JSON, with markdown code fences stripped. Invalid or missing fields are replaced with safe defaults (category→"General Inquiry", severity→"P3", confidence→0).

Step 6–7: Embeddings and Ticket Creation

How are embeddings generated and stored?Intermediate

Email embeddings are generated by Gemini's gemini-embedding-001 model, which natively returns 3072 dimensions. The SDK does not expose dimensionality control, so the code downscales via Matryoshka truncation (the model is trained for this) to match the Pinecone index dimension (default 768, configurable via PINECONE_EMBEDDING_DIMENSIONSorgs/{orgId}/emails with metadata (from_address, category, severity, timestamp). A separate embedding is also stored under orgs/{orgId}/tickets when a new ticket is created.

function toTargetDimension(values: number[]): number[] {
	const sliced = values.length > EMBEDDING_DIMENSIONS ? values.slice(0, EMBEDDING_DIMENSIONS) : values;
	const norm = Math.sqrt(sliced.reduce((sum, v) => sum + v * v, 0)) || 1;
	return sliced.map((v) => v / norm);
}

export async function generateEmbedding(text: string): Promise {
	const genAI = new GoogleGenerativeAI(process.env.GEMINI_API_KEY!);
	const model = genAI.getGenerativeModel({ model: "gemini-embedding-001" });
	const result = await model.embedContent(text);
	return toTargetDimension(result.embedding.values);
}

What happens when a new ticket is created versus when an email is added to an existing thread?Advanced

If the email is detected as a new thread (not a reply to an existing ticket), a new ticket row is created with all the classification data, and the email is linked with relationship="original". If it's a reply to an existing ticket, only a ticket_emails link is created with relationship="reply", and the existing ticket's severity is updated if the new email has higher priority. Both paths store the embedding and create audit logs.

Step 8: Auto-Response Generation

When and how is an auto-response generated?Advanced

Auto-responses are generated for non-spam emails with P3 or P4 severity only (P1/P2 never auto-respond). The function generates an embedding from the email subject and body, then semantically searches for matching FAQs by category. If the top match has similarity ≥ 0.9 (perfect match), the response is auto-sent; if 0.7–0.9 (partial match), it's saved as a draft suggestion for the agent; if <0.7, no response is generated. A Gemini call personalizes each suggested response using the top 3 matching FAQ answers. The auto-response record is saved to the database with sent: true/false and response_type: "auto"|"suggest"|"none".

What database rows are written during email processing, and in what order?Advanced

The order is: (1) emails row (upsert, for dedup safety), (2) tickets row (if new thread), (3) ticket_emails links (relationship: "original" or "reply"), (4) auto_responses row (if applicable, with sent=true/false), (5) audit_logs entry (with full classification and processing metadata). Pinecone vectors are stored in parallel with step 1. If an email is marked spam at step 1, only the email row is written and processing stops. If classified as spam by AI (step 5), the email row is updated with is_spam=true and processing stops before ticket creation.

Step 9: Pipeline Result and Error Handling

What does the pipeline return on success, and what error cases can occur?Advanced

On success, processEmail() returns an object with status="processed", email_id, ticket_id, ticket_number, classification, thread, customer, auto_response_sent, and processing_time_ms. On failure at any step, the function catches the error, saves a failed email (with processed=false) for retry, and returns status="error" with the error message. Spam-detected and duplicate-detected emails return status="spam" or status="duplicate" with the detection method and similarity score. The HTTP route responds with 200 on success (even if status is "spam" or "duplicate"), and 500 only if the entire request processing fails.
