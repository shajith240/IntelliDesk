How mail gets in

What actually triggers ingestion, and why is it GitHub Actions instead of Vercel's own cron?Basic

A GitHub Actions workflow calls the app's own HTTP endpoint every 10 minutes. The workflow file explains why it isn't Vercel's built-in cron: Vercel's free plan only allows a daily cron trigger, and GitHub Actions gives free scheduled runs on a public repository, so the schedule lives there instead. It POSTs $APP_URL/api/emails/poll with Authorization: Bearer $CRON_SECRET, with a 90s curl timeout and a 3-minute job timeout, and fails the job unless the response is HTTP 200. A concurrency group (poll-mailboxes, cancel-in-progress: false) means a slow run is never cancelled by the next scheduled tick — it just queues behind it.

on:
  schedule:
    - cron: "*/10 * * * *"
  workflow_dispatch: {}

concurrency:
  group: poll-mailboxes
  cancel-in-progress: false

What does GET/POST /api/emails/poll do, in order?Intermediate

Both GET and POST route to the same handler. It verifies the bearer token (verifyCronRequest), computes a deadline BUDGET_MS (50 seconds) ahead of now, then runs two phases sequentially: ingestAllMailboxes() (fetch new mail into the queue) followed by drainIntakeQueue(deadline) (process queued rows until the deadline). After both finish it deletes auth_login_attempts rows older than 30 days — unrelated to email, piggy-backed onto the same scheduled tick because the throttle window they exist for is only 15 minutes. The route declares maxDuration = 60, so the 50,000ms budget leaves roughly 10 seconds of headroom for the function to actually return before Vercel kills it.

Step 1 — Ingest: getting mail into the queue durably

Why is ingestion split into "ingest" and "drain" instead of one pass?Advanced

The file's own header comment states the reasoning directly: ingest fetches unseen mail and durably stores each message as an unprocessed row before marking it read (\Seen) in the mailbox, then drain processes stored rows until the time budget runs out. If a run times out mid-way, nothing is lost: unstored mail is still unread in the mailbox (a later poll will refetch it) and stored-but-unprocessed rows sit in emails for the next drain to pick up. This makes the whole thing an at-least-once pipeline, not exactly-once at the mailbox layer — exactly-once is instead enforced downstream by the message_id idempotency check in storeRawEmail and by record_inbound_message's own idempotency.

src/server/email/intake.ts:8-13
Walk through fetchUnseenMessages's store-then-\Seen ordering.Advanced

ingestAllMailboxes calls listPollableMailboxes() to get every organization's connected IMAP config, then for each one calls fetchUnseenMessages(config.imap, callback) where the callback is storeRawEmail. The naming and the module comment make the ordering explicit: each message is durably stored via the callback before the IMAP client marks it \Seen. That means a crash between "stored" and "marked seen" simply causes the same message to be refetched next poll — safe, because storage is idempotent on message_id. A mailbox whose fetch throws is counted in mailboxErrors and its sync failure recorded via recordMailboxSync, but does not stop the loop over the other organizations' mailboxes.

for (const { organizationId, config } of mailboxes) {
	try {
		const result = await fetchUnseenMessages(config.imap, (email) => storeRawEmail(email, organizationId));
		summary.fetched += result.fetched;
		summary.stored += result.stored;
		await recordMailboxSync(organizationId);
	} catch (err) {
		summary.mailboxErrors++;
		await recordMailboxSync(organizationId, err instanceof Error ? err : new Error(String(err)));
	}
}

How does storeRawEmail avoid storing the same message twice?Intermediate

If the message carries a message_id, it first does a scoped lookup (organization_id + message_id) and returns early without inserting if a row already exists. Only then does it insert. This is the idempotency layer that makes "store, maybe refetch later" safe: a message re-delivered after an interrupted run, or refetched because \Seen was never set, is stored exactly once. Messages with no message_id at all (malformed mail) are always inserted without a duplicate check.

if (email.message_id) {
	const { data: existing } = await supabaseAdmin
		.from("emails")
		.select("id")
		.eq("organization_id", organizationId)
		.eq("message_id", email.message_id)
		.limit(1)
		.maybeSingle();
	if (existing) return;
}

How does drainIntakeQueue select and claim rows, and what stops two overlapping runs from double-processing?Advanced

It selects up to 50 unprocessed rows (processed = false, processing_attempts < MAX_PROCESSING_ATTEMPTS, i.e. < 5) ordered oldest-received-first. For each row, before calling processEmail, it does a compare-and-set: an UPDATE that increments processing_attempts and sets last_attempt_at, filtered on id and processed = false and processing_attempts = row.processing_attempts (the value read a moment earlier). If a concurrent run already claimed and bumped that row, the filter no longer matches, .maybeSingle() returns null, and this run skips it (continue) instead of processing it a second time. This is the concurrency guarantee referenced in the function's own doc comment: "two overlapping runs never process the same email twice."

const { data: claimed } = await supabaseAdmin
	.from("emails")
	.update({ processing_attempts: row.processing_attempts + 1, last_attempt_at: new Date().toISOString() })
	.eq("id", row.id)
	.eq("processed", false)
	.eq("processing_attempts", row.processing_attempts)
	.select("id")
	.maybeSingle();
if (!claimed) continue; // another run took it
src/server/email/intake.ts:103-137
What is PACE_MS for, and how does the loop decide to stop before its budget runs out?Intermediate

PACE_MS = 4_000: after each processed row (except the last), the loop awaits a 4-second pause, so consecutive Gemini calls stay under free-tier per-minute rate limits. Before claiming each row, the loop checks Date.now() + PACE_MS > deadline — if there isn't even room for one more paced iteration, it sets summary.remaining = true and breaks, leaving the rest of the 50-row batch for the next scheduled run. If exactly 50 rows were fetched (the .limit(50) cap) and the loop still finished within budget, remaining is also forced true, since a full page means there could be more rows the query didn't even see.

src/server/email/intake.ts:19,122-126,172
What happens to a message that keeps failing? Is there a poison-message mechanism?Intermediate

Yes. The query that selects candidate rows filters on processing_attempts < MAX_PROCESSING_ATTEMPTS (5). Every claim increments processing_attempts regardless of whether processEmail succeeds, so after 5 failed attempts the row simply stops matching the query and is never selected again — it is left in the table, unprocessed, for manual inspection, rather than retried forever. On a genuine failure the row's processing_error column is also set (from the caught error message, truncated to 1000 chars) so an admin looking at the row can see why.

Cleaning, spam filtering and automated-mail detection

How is the body cleaned before anything else runs?Basic

If body_text is present and non-blank it's used as-is; otherwise body_html is run through stripHtml (strips <style>/<script>, turns <br> and block-closing tags into newlines, strips remaining tags, decodes basic entities, collapses whitespace). The result then goes through cleanEmailBody, which trims quoted-reply tails: it stops copying lines at the first "On ... wrote:" line, a "--- Original Message ---" banner, >>-quoted lines, or an Outlook-style "From: ... Sent: ... To:" block.

src/server/pipeline/processor.ts:52-58; src/server/email/parser.ts:7-45
What are the four kinds of automated mail, and which ones get ticketed?Advanced

detectAutomatedMail is pure logic (no I/O), unit-tested in tests/unit/automated-mail.test.ts. It checks, in order: is the sender this workspace's own mailbox address (own); is it a bounce — a mailer-daemon/postmaster-style sender, an empty Return-Path: <>, or a multipart/report with delivery-status (bounce); does it carry RFC 3834 Auto-Submitted (any value except literal no), an X-Autoreply/X-Autorespond header, Precedence: auto_reply, or an out-of-office-shaped subject (auto_reply); or does it look like bulk mail — Precedence: bulk/junk/list, mailing-list headers (List/List-Id/List-Unsubscribe), or a no-reply/do-not-reply/notifications@/alerts@ sender (bulk). The pipeline treats these very differently: processor.ts only short-circuits (skip ticketing entirely, mark processed, return "ignored") for own, bounce and auto_reply — the check is if (automated && automated.kind !== "bulk"). A bulk email (e.g. a newsletter) falls through and is ticketed normally; it is only ever prevented from being auto-answered later, via decideAutoSend's automatedReason check.

src/server/email/automated.ts:10-95; src/server/pipeline/processor.ts:64-79
There are two separate spam checks. What's the difference, and what does the "not spam" override do?Intermediate

Local (step 1): isLikelySpam(subject, body, from) is a zero-API-call keyword scorer — it adds points for promotional phrases (e.g. "limited time offer", "claim your prize"), automated-content phrases (e.g. "newsletter", "verification code"), a noreply/marketing-shaped sender (+2), more than 15 links in the body (+2), and a social-network sender like LinkedIn/Facebook (+3); score ≥3 flags it as spam, run entirely before any Gemini call. AI (step 5b): after classification, classification.is_spam (the model's own judgment) is checked separately, catching spam the keyword list misses. Both checks are skipped entirely when options.notSpam is true — set when the row's not_spam_at column is non-null, i.e. an admin already called POST /api/emails/[id]/not-spam to override a prior spam classification and the row is being reprocessed.

Embedding, dedup and thread detection

Where does the embedding used for dedup and search come from?Basic

ai = await getAiContext(orgId) picks the workspace's own Gemini key if one is saved, else the platform key. generateEmailEmbedding(ai, subject, cleanBody) concatenates subject and body (truncated to 5000 chars) and calls the shared generateEmbedding helper, which uses gemini-embedding-001, truncates the native 3072-dim output to the configured Pinecone dimension (Matryoshka truncation) and re-normalizes to unit length. This single embedding is reused for both the dedup/thread check and the Pinecone emails namespace upsert later — it is not recomputed.

src/server/pipeline/processor.ts:103-105; src/server/gemini/classify.ts:159-166; src/server/gemini/embeddings.ts:14-29
Exactly how does checkDuplicate tell an exact repeat from a semantic near-duplicate?Advanced

Two methods, tried in order. 1. Exact: if a message_id is present, look for an existing, already-processed, non-spam row with the same message_id in this org (excluding the current row's own id when reprocessing). A hit returns method: "message_id", similarity_score: 1.0. 2. Semantic: query the org's emails Pinecone namespace for the 5 nearest vectors to this embedding, filtered to the same from_address and a timestamp >= cutoff of received_at - 72h (DEDUP_TIME_WINDOW_HOURS). Matches are filtered to exclude the row's own vector id (excludeEmailId) — otherwise reprocessing an email already in Pinecone would always find itself as the closest match. If the top remaining match scores ≥ 0.85 (DEDUP_SIMILARITY_THRESHOLD), it's method: "semantic".

Only an exact Message-ID duplicate short-circuits the pipeline. What happens to a semantic near-duplicate?Advanced

In processEmail, the early-return only fires for dupResult.is_duplicate && dupResult.method === "message_id". A semantic-only match falls through to thread detection. If detectThread found nothing (!threadResult.existing_ticket_id) but the dedup check did find a semantic duplicate, processor.ts looks up which ticket the matched earlier email is attached to (via ticket_messages.email_id) and, if found, synthesizes a thread result with thread_type: "near_duplicate", confidence: dupResult.similarity_score. That means "the customer wrote again in different words" gets appended to their existing ticket instead of either being dropped or spawning a second ticket.

src/server/pipeline/processor.ts:120-160
List detectThread's match strategies in priority order, and what "our own outbound Message-IDs" has to do with it.Advanced

Priority, as stated in the function's own comment ("header match > ticket reference > subject+sender match > none"), every lookup scoped to organization_id:

  1. In-Reply-To header: exact match against any stored emails.message_id in this org — confidence: 1.0. Because every outbound reply is stored with its own Message-ID (via sendTicketReply → complete_ticket_reply, an outbound emails row), a customer's reply-to-our-reply matches here even though the matched row is one we sent, not one they sent.
  2. References header: same table, matched against the last 20 entries of the References list — confidence: 0.95.
  3. Ticket reference in text: extractTicketReferences pulls TKT-#####-shaped tokens (among other patterns) out of subject+body; a live match against tickets.ticket_number in this org gives confidence: 0.95.
  4. Fuzzy subject match: within the last 48 hours, same from_address, processed inbound emails in this org are fuzzy-matched on normalizeSubject (strips Re:/Fwd:/bracketed tags) using Fuse.js, threshold 0.3; a score <0.3 counts as a match, confidence: 1 - score.
  5. Otherwise thread_type: "none".

Classification, customer identification, and the commit point

What does the classification step return, and what happens if the AI call itself fails versus returns garbage?Advanced

classifyEmail wraps the customer text in an untrusted() delimiter and asks Gemini for a strict JSON object (category, severity P1–P4, language, sentiment, confidence, summary, key_entities, suggested_tags, requires_human_review, reasoning, is_spam) via responseSchema. Two distinct failure modes are handled differently: if the underlying call throws an AiCallError (outage, bad key, rate limit), it is rethrown unchanged — the pipeline's outer catch turns this into a status: "error" result and the email stays queued for retry, so an AI outage can never create a ticket with invented labels. If the call succeeds but the JSON is unparseable or otherwise unusable, the function instead returns a safe fallback object with requires_human_review: true and a P3/General Inquiry default, logging the parse failure. See AI Design & Safety for the full reliability story.

How does customer identification decide contact vs. account, and why does a personal-domain sender never get grouped into a company?Intermediate

Strategy, per the module comment: existing contact > company account by domain > new contact. identifyCustomer first looks up an existing contacts row by lowercased email; a hit returns immediately with method: "email_match". Why does the email get saved to the DB (step 7) before the ticket RPC, still marked unprocessed?Intermediate

saveEmailToDb upserts by the email's own id, with processed: false, right after classification and customer identification but before the Pinecone upsert and the ticket RPC. This gives the row a stable id that the subsequent Pinecone vector and ticket_messages.email_id foreign key can both reference. Since it's an upsert (not insert) on a primary key, calling it again on a retried run is harmless. The email only leaves the "unprocessed" state at step 13, after every downstream step succeeded — so a crash between step 7 and step 13 leaves a row that looks unprocessed and will be retried, not one that's silently lost or double-committed.

What exactly does record_inbound_message do, and how did it change between migration 010 and 013?Advanced

This Postgres function (called via supabaseAdmin.rpc) is the pipeline's single commit point. Its rules, straight from migration 010's comment (the Zendesk/Zammad convention):

  • reply to an open ticket (New/In Progress) → message appended, ticket untouched otherwise
  • reply to a Pending or Resolved ticket → appended and reopened to In Progress
  • reply to a Closed ticket → a brand-new follow-up ticket, linked via follow_up_of
  • severity only ever rises on an existing ticket, never falls (text comparison: 'P1' < 'P2'), via CASE WHEN v_severity IS NOT NULL AND v_severity < severity THEN v_severity ELSE severity END

It is idempotent per email: it first checks whether ticket_messages.email_id = p_email_id already exists (that column is UNIQUE) and, if so, returns the existing ticket with created: false, reopened: false instead of inserting again — this is what makes retrying a failed run safe even after the commit point already ran once. Migration 013 (normalize_contract) re-created the same function as part of the schema's expand/contract normalization: it dropped the ai_confidence column from the ticket INSERT (confidence is now read out of the ai_classification jsonb instead of being stored twice) and dropped performed_by from the reopened-ticket audit-log insert. The business logic — append/reopen/follow-up/new, idempotency, priority-only-rises — is unchanged between the two versions.

The other two ways mail gets in: webhook and bulk import

How does the ingest webhook (POST /api/emails/ingest) differ from the cron path?Intermediate

It authenticates with a separate bearer secret (EMAIL_INGEST_SECRET, via the same verifyBearerSecret helper), validates required fields (from_address/subject/received_at/organization_id) and that organization_id is a real UUID matching an existing org, builds a RawEmail from the JSON body, and calls processEmail(rawEmail, orgId) directly — there is no queue row and no drainIntakeQueue involved; it runs the pipeline synchronously inside the HTTP request and returns the PipelineResult as JSON (500 if status === "error", else 200). This means a webhook-delivered email that errors is not automatically retried by anything in this codebase — the caller (the external email-service webhook) is responsible for retrying based on the non-200 response.

src/app/api/emails/ingest/route.ts:1-83
How does POST /api/emails/bulk (admin import) differ, and what are its limits?Basic

Session-authenticated (requireAuth + can.importEmails, admin-only), not bearer-token like the other two intake routes. It requires a non-empty emails array capped at 50 per request, maps each entry into a RawEmail, and calls processEmailBatch(rawEmails, orgId), which runs processEmail once per email in a simple for loop with a 4-second pause between calls (default delayMs = 4000, the same figure as the queue drain's PACE_MS). It returns a summary (total/success/duplicates/spam/errors) alongside every individual PipelineResult. Like the webhook, there's no queue and no retry: an email that errors here is simply reported as an error in the response.
