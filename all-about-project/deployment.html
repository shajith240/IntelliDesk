Deployment & DevOps

How this application is deployed to Vercel, how scheduled jobs are configured, and what environment variables and local vs. production differences apply.

Vercel deployment model

How is this application deployed to Vercel?Basic

The app is a standard Next.js application deployed to Vercel using its default configuration:

  • Repository root — The app lives at the repository root, not in a subfolder. Vercel's default "Root Directory" setting points to the repo root, so no custom path is needed.
  • Framework preset — Next.js (automatically detected by Vercel).
  • Build command — npm run build (default for Next.js); the build runs next build, which produces a production-optimized bundle with the React Compiler enabled.
  • No static export — The app requires route handlers, server-side authentication, and dynamic data from Supabase, so static export is not used.
  • Runtime features — Next.js App Router, dynamic routes, API routes, middleware, and cron jobs are all supported.

How is NEXTAUTH_URL configured differently in development vs. production?Intermediate

The NEXTAUTH_URL environment variable tells NextAuth where the app is running, so it can validate redirect URLs and session cookies:

  • Local development — NEXTAUTH_URL=http://localhost:3000 (set in .env.local).
  • Production — NEXTAUTH_URL must be set to the deployed Vercel URL (e.g., https://intellidesk-ai.vercel.app) in the Vercel dashboard under Settings → Environment Variables.

If NEXTAUTH_URL is not set correctly, NextAuth will reject sign-in requests and return a "NEXTAUTH_URL is not set" error. Vercel automatically sets AUTH_TRUST_HOST=true at runtime, so Auth.js trusts Vercel's request headers; no manual configuration is needed there.

Scheduled cron jobs

How is the email polling cron job configured?Intermediate

Vercel Cron reads the schedule from vercel.json in the repository root:

{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "crons": [{ "path": "/api/emails/poll", "schedule": "0 6 * * *" }]
}

This configures a daily trigger at 06:00 UTC. Vercel automatically sends an Authorization: Bearer $CRON_SECRET header to the endpoint; the secret is read from the environment variables you set in the Vercel dashboard. The endpoint checks that header via the verifyCronRequest() function and fails closed (503) if the secret is not configured.

The schedule format is POSIX cron syntax (minute hour day month day-of-week, all in UTC). The Vercel Hobby plan only allows a single daily schedule; Pro and higher plans support more frequent schedules (e.g., */10 * * * * for every 10 minutes).

What does the /api/emails/poll endpoint do when the cron job runs?Intermediate

The endpoint is defined in src/app/api/emails/poll/route.ts. When called by Vercel Cron (or manually via curl with the CRON_SECRET), it:

  • Verifies the bearer token matches CRON_SECRET using timing-safe comparison (no timing-side-channel vulnerability).
  • Polls every organization's IMAP mailbox connection (stored in Supabase under email_config).
  • For each new unseen email, parses it, extracts the From/To/Subject, checks for spam/duplicates, and identifies the customer thread.
  • Creates or updates a ticket in the tickets table, storing the email with its SLA due dates computed from the org's policies.
  • Generates an AI classification (category, priority, sentiment) and an embedding via Gemini.
  • Stores the embedding in Pinecone under the org's namespace for later retrieval during reply drafting.
  • Logs every step to the audit_logs table.

The endpoint has a 60-second max duration in Next.js; any emails not processed in that time are picked up by the next scheduled run.

Why does the cron endpoint fail with 503 instead of 401 if the secret is missing?Intermediate

By design, if CRON_SECRET is unset in the environment, the endpoint returns 503 Endpoint is not configured rather than silently accepting all requests or returning a generic 401 that looks like "you sent the wrong secret."

This "fail closed" approach makes misconfiguration immediately obvious: if someone deploys without setting the secret, the cron job will fail loudly and visibly in the Vercel dashboard, rather than silently skipping email polling. The 503 status also signals to Vercel that the job should be retried, so it doesn't give up after one failure.

Environment variables by purpose

What environment variables are required for the app to run, grouped by purpose?Intermediate

Supabase (database and auth storage):

  • NEXT_PUBLIC_SUPABASE_URL — Project URL (public, safe to commit in .env.local)
  • NEXT_PUBLIC_SUPABASE_ANON_KEY — Public API key for auth flows (public)
  • NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY — Publishable key (public)
  • SUPABASE_SERVICE_ROLE_KEY — Secret key for unrestricted database access from route handlers (server-only, never in browser)

NextAuth (session management):

  • NEXTAUTH_SECRET — Random secret for signing JWT sessions; generate with openssl rand -base64 32
  • NEXTAUTH_URL — Canonical app URL (e.g., http://localhost:3000 locally, https://app.vercel.app in production)

Google Gemini (classification and embeddings):

  • GEMINI_API_KEY — API key from Google AI Studio (server-only)

Pinecone (vector search):

  • PINECONE_API_KEY — API key (server-only)
  • PINECONE_INDEX — Index name (e.g., "intellidesk")
  • PINECONE_HOST — Optional: direct index host URL from the Pinecone console
  • PINECONE_EMBEDDING_DIMENSIONS — Dimension count (3072 for Gemini embedding model; must match index creation)

Cron and webhooks (scheduled jobs):

  • CRON_SECRET — Bearer token for Vercel Cron to call /api/emails/poll and /api/emails/process-queue (server-only); generate with openssl rand -hex 32
  • EMAIL_INGEST_SECRET — Bearer token for external mail relay to call /api/emails/ingest webhook (server-only); generate with openssl rand -hex 32

Optional development features:

  • NEXT_PUBLIC_DEMO_MODE — If true, shows "Load sample tickets" action in empty states (local development only)
  • IMAP_USER — Optional: local IMAP user email for filtering self-sent emails during testing

What is the difference between public and server-only environment variables?Basic

Public variables (prefixed with NEXT_PUBLIC_) are compiled into the client-side JavaScript bundle and are safe to commit to version control. Examples: Supabase URL and public keys, which are safe because Supabase has row-level security (RLS) policies that enforce per-user/per-org access control.

Server-only variables (no prefix) are never sent to the browser; they are available only to route handlers and server-side functions. Examples: SUPABASE_SERVICE_ROLE_KEY (bypasses RLS), GEMINI_API_KEY, and CRON_SECRET. These must be set in the Vercel dashboard, never committed to git.

The Next.js build will not fail if you accidentally use a server-only variable on the client, but the server-only package and ESLint's no-restricted-imports rule catch the mistake at lint time.

What happens if you run npm start locally without setting AUTH_TRUST_HOST?Intermediate

When running a production Next.js build outside of Vercel (via npm start), Auth.js (NextAuth v5) checks the request's Host header against the configured NEXTAUTH_URL. If they don't match, it rejects the request as a potential host header injection attack.

Setting AUTH_TRUST_HOST=true` disables this check and tells Auth.js to trust the Host header. This is necessary when running a production build locally or in a non-Vercel environment:

AUTH_TRUST_HOST=true npm start

Vercel automatically sets AUTH_TRUST_HOST=true at runtime, so the variable doesn't need to be configured in the Vercel dashboard. Local development with npm run dev` handles it automatically as well.
