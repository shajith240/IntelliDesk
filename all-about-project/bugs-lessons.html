Bugs & Lessons

Every significant bug found in the project — security holes, data-loss bugs, logic errors and UI defects — with how it was found, the root cause, the fix, and the lesson. Many were found by auditing the code against how mature helpdesks behave, or by tests written to prove a rule.

Security incidents

What was the most serious security problem found?Advanced

The Supabase Data API was open. Row-level security was disabled and the anon and authenticated roles held full privileges on every table. Supabase's anon key is public by design (it ships to browsers), so anyone holding it could read password hashes and mailbox credentials through PostgREST. The RLS policies written earlier relied on auth.uid(), which is always null because the app uses NextAuth, not Supabase Auth.

Fix (migration 006): RLS on everywhere with no policies, all privileges revoked from browser roles (including default privileges for future objects), legacy tables moved to an unexposed schema. The app is unaffected because it uses the service role on the server only.

Lesson: "we set up RLS" means nothing until you check which role actually holds which grant. Closed by default, opened deliberately.

Data-loss and correctness bugs

How could customer email be lost, and how was that fixed?Advanced

Three separate ways:

  1. Marked read before stored. Mail was flagged \Seen when fetched; if the serverless function timed out before processing, the email was gone. Now it's stored first and flagged after (at-least-once).
  2. Marked processed before ticketed. The pipeline set processed = true early; a later failure left an email "done" but on no ticket. Now the flag is the last write, after the idempotent commit point.
  3. Near-duplicates discarded. A follow-up very similar to the sender's earlier email was dropped as a duplicate. Now it is attached to that ticket; only a re-delivery of the same Message-ID is dropped.
src/server/email/imap.ts:96-101; src/server/pipeline/processor.ts:236, 313
Why could a retry create a duplicate ticket or silently skip an email?Advanced

The email's vector was written to Pinecone before its ticket was created. When a later step failed and the email was retried, semantic duplicate detection found the email's own vector with similarity 1.0 and discarded it as a duplicate. Separately, ticket creation and linking the email were two calls, so a crash in between left a ticket with no conversation. Fixes: the deduplicator ignores the email's own id, and record_inbound_message() creates the ticket and first message in one idempotent transaction.

src/server/pipeline/deduplicator.ts; supabase/migrations/010_record_inbound_message.sql
What was the "AI drafts never saved" bug?Intermediate

The reply generator returns a type of "auto" or "suggest", but the insert wrote that value into auto_responses.match_type, whose CHECK constraint only allows perfect, partial or none. Every insert failed, and the code didn't check the error, so the feature silently did nothing: the table was empty in production. Found while verifying data before a migration; fixed by mapping the value and by treating insert errors as failures.

Lesson: an ignored database error is a silent feature outage. Check error on every write.

Bugs caught by tests and rehearsals

What did the tests and migration rehearsals catch before production?Intermediate
  • Bounce detection: mailparser returns Content-Type as { value, params }; the detector read only value and missed delivery reports. The unit test failed on its first run.
  • Generated column in a foreign key: Postgres rejects ON DELETE SET NULL on such a key; the rehearsal failed, and the design changed to NO ACTION (arguably better).
  • Constraint ordering: a table referencing a composite key was created before the key existed.
  • Existing constraint name collided in 007.
  • Seed data inconsistency: 14 tickets had a confidence but no AI verdict, found when preparing the generated column, and backfilled first.
  • Test assumptions: a test tried to backdate a resolution time in the same statement as the status change; the new trigger (correctly) overrode it. The test was wrong, not the trigger.
testing.html; database-design.html
What surprised you about PostgREST?Advanced

Two things. After adding a foreign key, PostgREST's schema cache must be reloaded (NOTIFY pgrst, 'reload schema') before embeds work. And it didn't detect the self-referencing composite foreign key tickets.follow_up_of for embedding at all, so the parent ticket is loaded with a second query. Knowing when to stop fighting a tool is part of the job.

UI bugs

Which UI bugs were fixed?Basic
  • Unwanted focus rings: a global :focus-visible rule overrode components' outline-none; fixed by moving it into @layer base.
  • Horizontal scrolling in the queue: fixed with container queries shared by header and rows.
  • Duplicate element ids: components render twice (desktop and mobile layouts); ids now come from useId.
  • Double-sending a reply: a ref-based guard blocks a second submit while one is in flight.
  • A hint text laid out in pieces: a flex container split inline text and a link into separate columns; wrapped in a single span.

Lessons

What are the main engineering lessons from this project?Intermediate
  1. Put invariants in the database. Every rule that "the code always does" was eventually broken by some other code path.
  2. Silent failures are the worst failures. Ignored errors hid a dead feature (drafts) and dropped audit rows.
  3. Serverless means "may stop at any line". Design every multi-step job to be retried safely: store first, commit once, mark done last.
  4. Test rules by trying to break them, against real data, inside a rollback.
  5. Change live schemas in expand/contract steps.
  6. AI output is untrusted input too. Ground it, gate it, label it, and let it fail closed.
  7. Remove what isn't used (dead routes, env vars, columns): each one is a place for bugs to hide.
