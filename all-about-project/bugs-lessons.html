Bugs Fixed & Lessons Learned

Concrete bugs found and fixed during this project, with the root cause and the fix. Framed as "what broke, why, how it was found, how it was fixed" — the shape interviewers usually want.

CSS & layout bugs

A global focus-ring style kept appearing where components explicitly said outline-none — what caused it?Advanced

Symptom: the command palette's search input and the queue's search box showed a thick blue focus outline even though their own classes included outline-none / a custom thin focus ring. It happened inconsistently — some inputs were affected, some weren't.

Root cause: the project's global :focus-visible rule (2px solid ring on every focusable element) was written directly in globals.css, outside any Tailwind @layer. In Tailwind v4's cascade, un-layered CSS has higher priority than utility classes emitted inside Tailwind's own layers — so the global rule was beating component-level outline-none/focus-visible:ring-* utilities regardless of source order, which is why it looked "random."

Fix: moved the base rules (box-sizing reset, body defaults, the focus-visible ring, selection color) into an explicit @layer base block, so component utility classes — which Tailwind emits into a later layer — can override it as intended.

/* In a layer so component utilities (outline-none, focus-visible:ring-*) can override these. */
@layer base {
  :focus-visible {
    outline: 2px solid hsl(var(--ring));
    outline-offset: 2px;
  }
}
src/app/globals.css:202 — @layer base wrapping the reset/focus rules
Why did the SLA risk panel and the queue table both develop horizontal scrolling / overlapping content at narrow widths, and how was it fixed?Intermediate

Symptom: at 390px viewport width, the SLA risk panel's rail and the Command Center's grid had visible horizontal page scroll; the panel's "Open" button and SLA badge could visually collide.

Root cause: a CSS grid declared only a wide breakpoint's column template (e.g. xl:grid-cols-[minmax(0,1fr)_360px]) with nothing for the base/mobile case. Without an explicit base grid-template-columns, the grid falls back to an implicit, content-sized auto column, which doesn't shrink below its content's natural width — producing overflow instead of wrapping.

Fix: every such grid was given an explicit single-column base template (grid-cols-[minmax(0,1fr)]) before the wider breakpoint kicks in, and the SLA panel's rows were restructured with min-w-0 truncate on the text sibling of any fixed-width button so long content truncates instead of pushing the button out of view.

className="grid grid-cols-[minmax(0,1fr)] gap-6 lg:grid-cols-2"
src/features/command-center/components/command-center.tsx:101; the same base-track fix was applied to src/components/command-center/CommandCenterFallback.tsx, src/features/analytics/components/analytics.tsx, and src/features/settings/components/mailbox-form.tsx
The ticket queue used to require horizontal scrolling on narrow screens. What was the actual fix, not just "make it responsive"?Advanced

The original queue was a fixed-width HTML <table> wrapped in overflow-x-auto, which is the standard "just let it scroll" escape hatch — but the product requirement was that it must never scroll horizontally, at any width, in any container. The fix replaced the table with a <ul> of rows using CSS Grid with Tailwind v4 container queries (@container on the wrapper; @min-[560px]:grid-cols-[...], @min-[860px]:..., @min-[1100px]:..., @min-[1240px]:... on the row template), so columns are sized against the queue's own rendered width rather than the viewport. Below the first tier it renders as a 2-line card instead of a row. The column template is defined once in a shared module and imported by both the real rows and the loading skeleton, so they can't silently drift apart.

src/features/queue/lib/grid.ts — ROW_GRID / HIDE_860 / HIDE_1100 / HIDE_1240, imported by both queue-list.tsx and queue-skeleton.tsx

React & state bugs

A ticket's conversation heading had a broken accessible label and a broken test selector — what was wrong?Intermediate

Symptom: a Playwright locator for the conversation heading resolved to 37 matching, mostly hidden elements instead of one.

Root cause: the ticket workspace renders up to three parallel responsive layouts (desktop 3-column, tablet, and a mobile tabbed layout) simultaneously in the DOM, toggling visibility with CSS rather than unmounting the inactive ones. The conversation column's heading used a hardcoded string id (id="conversation-heading") for its aria-labelledby target — fine for one instance, but every responsive layout variant rendered its own copy of the same component, producing multiple elements with the same id in the document at once, which is invalid HTML and breaks both the accessibility tree and any selector that assumes uniqueness.

Fix: replaced the hardcoded string with React's useId(), which generates a unique id per component instance.

const headingId = useId();
// ...
<section aria-labelledby={headingId}>
  <h2 id={headingId}>...

How is double-submission prevented when an agent clicks "Send response" on a ticket reply, and why is a boolean return value from send() significant?Advanced

Sending a reply is a real, irreversible side effect — it emails a customer and marks the ticket resolved — so the send path has two layers of protection: a useRef in-flight flag checked synchronously at the top of send() (refs, unlike state, update immediately without waiting for a re-render, which matters if the button is clicked twice within the same tick), and the button itself is disabled while a request is outstanding.

The confirmation dialog originally closed unconditionally after calling send(); the fix made send() return a Promise<boolean> — true only on a verified successful response — so the dialog closes on success and stays open, showing the server's error message, on failure. Closing on click regardless of outcome would have hidden a failed send from the agent while the ticket silently remained unresolved.

const sendingRef = useRef(false);
const send = useCallback(async (): Promise<boolean> => {
	if (!pending || sendingRef.current || status === "sending") return false;
	...
	sendingRef.current = true;
	...
} finally {
	sendingRef.current = false;
}
src/features/ticket-workspace/hooks/use-reply-draft.ts:90 (sendingRef), :95-96 (Promise<boolean> signature and guard)

Investigations that turned out not to be code bugs

/api/dashboard was observed taking 33–75 seconds on one occasion. What was the actual cause, and how was it diagnosed?Intermediate

Rather than assuming the route's own logic was the bottleneck, each of the dashboard's underlying Supabase queries was timed individually and directly (bypassing the Next.js route) using the service-role client in a standalone script. Every individual query — ticket counts, SLA policies, recent audit log rows — came back in roughly 280–370ms, both during the slow observation and afterward. A raw fetch to the Supabase REST root also returned in under 150ms. This ruled out the application code (a slow query, an N+1, a missing index) and pointed to a transient network/infrastructure condition on Supabase's side; a repeat request minutes later completed in about 2 seconds, the expected range for the route's combined queries.

Lesson: time the dependency directly before assuming the bug is in your own code, especially for a latency spike that doesn't reproduce consistently.

Why does running the production build locally with npm start require setting AUTH_TRUST_HOST=true, when neither Vercel nor npm run dev need it?Basic

Auth.js (NextAuth v5) rejects requests whose Host header doesn't match a trusted value unless it can determine the deployment is on a known-trusted platform. Vercel sets the trust automatically at the platform level, and the Next.js dev server is exempted; a plain local production server (next start) is neither, so it needs the escape hatch explicitly. This surfaced as login silently failing (redirecting back to /login with no visible session) the first time the production build was run locally for testing, traced by reading the server log, which had an explicit UntrustedHost error.

Security fixes

What was wrong with the original /api/emails/poll and /api/emails/process-queue endpoints, and how was it found?Advanced

Both endpoints — which trigger real IMAP polling and email processing — had no authentication check at all and were reachable by anyone who knew the URL; /api/emails/ingest accepted an organization_id directly from the unauthenticated request body, meaning a caller could write data into any organization's ticket queue by simply naming its id. This was found by reading the route handlers directly rather than assuming existing endpoints were already gated, alongside the sibling question of what the outbound cron target should even be. The fix added a shared bearer-secret check (see the Engineering Decisions page for verifyBearerSecret) in front of all three routes, each keyed to its own secret so the polling/queue-processing secret and the inbound-ingest secret are independently rotatable.

src/server/auth/cron.ts; guards added to src/app/api/emails/poll/route.ts, src/app/api/emails/process-queue/route.ts, src/app/api/emails/ingest/route.ts
General pattern across this list Most of these bugs were found by directly measuring or directly reading — timing each query by hand instead of guessing, reading the actual route handler instead of assuming it was already guarded, reading the CSS cascade order instead of assuming "outline-none should just work." None were found by a test suite, because none exists yet — see the Testing Strategy page for what that implies and what a first test suite for this project should prioritize.
