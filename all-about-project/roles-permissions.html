Roles & Permissions

The three roles, the complete permission matrix, how ticket assignment works, and how each rule is enforced in three places: the UI hides what you can't do, the API refuses it, and the database refuses it again.

The roles

What are the roles and what is each for?Basic
RoleWhoIn one line
adminSupport lead / ownerRuns the workspace: sees everything, is the only role that assigns tickets, manages team, mailbox, AI and knowledge base
agentSupport staffWorks only the tickets an admin assigned to them
viewerManager, stakeholderRead-only access to the whole workspace; can never hold a ticket
export const can = {
	/** See every ticket in the organization (agents only see their own). */
	viewAllTickets: (s: Actor) => isAdmin(s) || isViewer(s),
	assignTickets: isAdmin,
	manageTeam: isAdmin,
	manageSettings: isAdmin,
	manageKnowledgeBase: isAdmin,
	importEmails: isAdmin,
	/** Admins and agents appear in the assignee pool and can mark themselves (un)available. */
	setOwnAvailability: (s: Actor) => isAdmin(s) || isAgent(s),

	viewTicket(s: Actor, ticket: AssignableTicket) {
		return isAdmin(s) || isViewer(s) || (isAgent(s) && ticket.assigned_agent === s.user.id);
	},

	/** Change status/priority/category and send replies. */
	workTicket(s: Actor, ticket: AssignableTicket) {
		return isAdmin(s) || (isAgent(s) && ticket.assigned_agent === s.user.id);
	},
};

How are pages protected, and where does each role land?Basic

The middleware sends anyone without a session on /dashboard/* to the login page. Each dashboard page then calls requirePageRole in the server component; a role that isn't allowed is redirected to its home: agents to My Work, everyone else to the Command Center. The sidebar only lists pages the role can open (each nav item declares its roles).

function homeFor(role: UserRole): string {
	return role === "agent" ? "/dashboard/my-work" : "/dashboard";
}

Assignment

Why do agents get 404 instead of 403 for other people's tickets?Intermediate

A 403 would confirm that the ticket id exists. Answering 404 for both "doesn't exist" and "not yours" lets agents learn nothing about tickets outside their queue. The same scoping applies to the ticket list, search results, the dashboard numbers and "similar tickets".

How is a ticket assigned, step by step?Advanced
  1. The admin opens the assign menu; candidates come from /api/team/workload, ranked available first, then by fewest open tickets.
  2. POST /api/tickets/[id]/assign checks can.assignTickets and calls assign_ticket(org, ticket, assignee, actor, note).
  3. In one transaction the function verifies the actor is an active admin of this organization, locks the ticket (FOR UPDATE), updates the assignee, inserts ticket_assignments history and writes a ticket_assigned / ticket_unassigned audit row.
  4. The enforce_ticket_assignee trigger rejects an assignee who isn't an active admin or agent of the same organization, and the composite foreign key independently rejects cross-tenant users.

Could an agent assign a ticket to themselves through some other route?Advanced

No. PATCH /api/tickets/[id] refuses assigned_agent for everyone (as well as SLA timestamps, ticket number and organization); the assign route is admin-only; and even a direct database call to assign_ticket with an agent as actor raises insufficient_privilege. The database tests include exactly that attempt.

How do tickets needing human review reach a person?Intermediate

The classifier sets is_flagged_for_review (low confidence, refunds, legal, angry customers…). Open, unassigned, flagged tickets appear in Needs Review (/dashboard/review, ?view=review) with a count in the sidebar. The admin assigns each to an available teammate from the ranked list.

What does "available" mean, and how is it different from "active"?Basic

is_active means the account is enabled (an admin can deactivate it; inactive users can't sign in). is_available is a person's own "I can take tickets" flag, toggled from the user menu, used only to rank assignment candidates. Viewers have neither role in assignment.

Team management rules

What rules protect the team and the workspace?Intermediate
  • Only admins add members; a new member gets a random 16-character initial password shown once to the admin.
  • An admin can't remove their own admin access ("Ask another admin to do it").
  • A workspace must always keep at least one active admin.
  • Deactivating a member, or making them a viewer, releases their open tickets back to the pool through assign_ticket(…, null), with the reason recorded in the history.
  • A deactivated user's session ends within 5 minutes (JWT re-validation) and they can no longer sign in.

How does the UI reflect permissions?Basic

useCanWorkTicket mirrors the server rule so the composer, status menu and priority controls become read-only for viewers and for agents on tickets that aren't theirs; the assign menu, Settings, Spam and knowledge-base editing only render for admins. This is convenience only — every action is re-checked by the API and database.

export function useCanWorkTicket(ticket: { assigned_agent: string | null }): boolean {
	const { data: session } = useSession();
	const role = session?.user.role;
	return role === "admin" || (role === "agent" && ticket.assigned_agent === session?.user.id);
}
