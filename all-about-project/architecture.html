System Architecture Overview

The shape of the app: a Next.js 16 monolith with App Router, layered into app routes, feature domains, and shared code. No microservices, no realtime updates — a single build that runs on Vercel, polls data from Supabase, and reaches out to Gemini, Pinecone, and IMAP/SMTP.

High-level structure

What type of app is this — monolith, microservices, something else?Basic

A Next.js 16 monolith running on Vercel. Everything ships in one build artifact. There are no separate backend services, job queues, or worker processes — the app is the only code running on Vercel. Cron-triggered HTTP endpoints inside the app handle the email polling and queue processing.

What's the folder structure under src/ and why is it organized that way?Intermediate

The structure is app → features → shared, enforced by import boundaries:

  • src/app/ — routes only: pages, layouts, API handlers. Imports from features and shared.
  • src/features/ — seven product-area folders (analytics, auth, command-center, knowledge-base, queue, settings, ticket-workspace), each with components/, hooks/, and lib/. Never import other features except one exception: command-center imports queue's WorkQueue component.
  • src/components/ — shared UI: ui/ (23 design primitives with zero business logic) and layout/ (12 app-shell components like the sidebar and command palette).
  • src/server/ — 19 server-only files: auth config, Supabase client, Gemini integration, IMAP/SMTP, the email pipeline. Every file starts with import "server-only";.
  • src/hooks/, src/lib/, src/types/ — shared utilities available to all layers.

This layering keeps business domains separate while preventing accidental leaks of server secrets into browser bundles.

How does the app prevent server secrets from being imported into browser code?Intermediate

Two layers: every file under src/server/ opens with import "server-only";, a package Next.js bundles. If that module is ever pulled into a client bundle, the build fails immediately. Additionally, an ESLint no-restricted-imports rule blocks importing @/server/* from shared code, features, or components — so the mistake is caught in the editor before a build is even attempted.

Request flow & routing

Walk me through the full flow for a page load, from the browser hitting the app until React renders. Intermediate

Browser hits /dashboard/tickets. Middleware (before any route handler runs) checks if the user is logged in via the NextAuth session. If not logged in, it redirects to /login with the original path as a callback. If logged in, it passes through to the route handler.

The route handler for that page is at src/app/dashboard/page.tsx. The dashboard layout (src/app/dashboard/layout.tsx) wraps the page and renders the app shell (sidebar, top bar) plus a Suspense boundary around the TicketWorkspace modal component. The root layout at src/app/layout.tsx wraps everything, loading fonts and calling the Providers component. The app streams the initial HTML to the browser, and React hydrates it into an interactive component tree. After hydration, the client-side SWR hooks start polling the API for data.

// src/middleware.ts: auth check
const isLoggedIn = !!req.auth?.user;
if (isDashboard && !isLoggedIn) {
  const loginUrl = new URL("/login", req.url);
  loginUrl.searchParams.set("callbackUrl", pathname);
  return NextResponse.redirect(loginUrl);
}

How does the app fetch data on the client side? Does it have websockets?Basic

The client uses SWR (Stale-While-Revalidate) to poll the app's own API routes. SWR is configured with dedupingInterval: 2000 (never make the same request twice within 2 seconds) and errorRetryCount: 3. In the README, it states "Data refreshes every 30 seconds." There are no websockets — no socket.io, no realtime subscriptions. A change made by one agent can take up to 30 seconds to appear in another agent's dashboard.

src/app/providers.tsx lines 27-33 define SWRConfig with dedupingInterval: 2000 and errorRetryCount: 3; README.md line 208 states "Data refreshes every 30 seconds and after every mutation. The status indicator in the top bar reflects whether the last refresh succeeded — the app polls and does not use a push/realtime connection."

Data access & security

How does an API route know which organization to return data for?Intermediate

Every authenticated API route calls requireAuth() to verify the user's session, then getOrgId(session) to extract their organization_id. Then it filters all queries to that organization using .eq("organization_id", orgId). This is the primary access-control mechanism — the database has no foreign-key constraints forcing org membership, so the application code is responsible for scoping every read and write.

const session = await requireAuth();
const orgId = getOrgId(session);
let query = supabaseAdmin
  .from("tickets")
  .select("...")
  .eq("organization_id", orgId);
src/app/api/tickets/route.ts lines 15-72; src/server/auth/helpers.ts defines requireAuth(); src/server/auth/org-context.ts defines getOrgId()
What is row-level security (RLS) used for if application code is doing the access control?Advanced

Row-level security is configured in the database but acts as defense-in-depth, not the primary control. The app uses the Supabase service-role key, which bypasses RLS entirely. RLS policies exist to protect against: (1) a future client-side feature that uses the anon key instead of the service-role key, or (2) an accidental cross-org data leak if a developer forgets the .eq("organization_id", orgId) filter. The policies ensure that if the primary layer fails, the database itself stops the leak.

supabase/migrations/003_rls.sql line 20-21 state: "The application uses supabase service_role key which BYPASSES RLS. These policies are defense-in-depth for any future use of anon/user keys."; README.md "Security notes" confirms the service-role key is used from route handlers only and must never reach browser code

Request lifecycle details

How does the app handle an API call from the client — what's the full path from the browser hook to the database and back?Advanced

A React component uses the useApi hook (built on SWR) to call GET /api/tickets. The hook sends the request with the browser's session cookie (set by NextAuth). The route handler at src/app/api/tickets/route.ts receives the request, calls requireAuth() to verify the session, extracts organization_id, builds a Supabase query filtered to that org, and returns the paginated, sorted list. The response is a JSON object with { tickets: [...], total, page, limit, total_pages }. The client SWR hook receives it, stores it in memory, and triggers a re-render. If the session expires (API returns 401), the error handler redirects to login.

src/app/providers.tsx lines 16-21 define the handleSwrError function that catches 401s and redirects to login; src/app/api/tickets/route.ts implements the full GET handler with auth, org-scoping, filtering, sorting, and pagination; src/types/api.ts line 38-44 define TicketListResponse shape
How are cron-triggered email endpoints protected, given they don't have a user session?Intermediate

/api/emails/poll and /api/emails/process-queue are called by Vercel Cron, not by a logged-in user. They authenticate with Authorization: Bearer $CRON_SECRET, checked against an environment variable using timingSafeEqual (resistant to timing attacks). If the secret is unset, the endpoint returns 503 "Endpoint is not configured" rather than silently accepting all requests — it fails closed and is diagnosable from the response alone.

src/server/auth/cron.ts implements verifyBearerSecret() and verifyCronRequest() with timingSafeEqual; README.md "Environment variables" section documents CRON_SECRET and the 503 fail-closed behavior at line 103
