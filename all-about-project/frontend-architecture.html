How do server and client components divide the work?Intermediate

Dashboard pages are small server components: they call requirePageRole (redirecting before any HTML is sent), set metadata and render a feature component inside Suspense. The interactive feature components are client components that fetch through SWR. src/app/providers.tsx is the client root: NextAuth's SessionProvider, next-themes, a global SWRConfig (2 s dedupe, 3 retries, no retry on 4xx, redirect to login on 401 keeping the current URL), tooltips and toasts. The dashboard layout is force-dynamic because every page depends on the session.

src/app/providers.tsx:1-30; src/app/dashboard/layout.tsx:1-18; src/app/dashboard/review/page.tsx
How does the ticket workspace open on top of any page?Intermediate

The dashboard layout renders the TicketWorkspace sheet next to every page. It reads the open ticket from the ?ticket=<id> URL parameter via useTicketParam: opening pushes a history entry, closing replaces it, so the workspace survives refresh, back/forward and can be shared as a link. The sheet warns before discarding an unsent draft.

src/hooks/use-ticket-param.ts:6-25; src/app/dashboard/layout.tsx; src/features/ticket-workspace/components/ticket-workspace.tsx
Which compiler/framework features are on?Basic

Next.js 16 App Router with React 19 and the React Compiler (reactCompiler: true), which memoizes automatically — so code avoids manual memoization tricks and uses compiler-safe patterns such as "adjust state during render" instead of effects for derived resets. TypeScript strict, Tailwind v4.

How is navigation role-aware, and what shortcuts exist?Basic

nav.ts is the single definition of navigation: each item has a label, icon, shortcut and the roles that may see it. The sidebar, the command palette (/ or Ctrl K) and the G-prefixed shortcuts all read it, so a role never sees a link or shortcut to a page it can't open. Shortcuts: G D Command Center, G R Needs Review, G I Incoming Queue, G M My Work, G A Analytics, G K Knowledge Base, G S Settings, G J Spam; ? shows them all; j/k and Enter move through lists.

Data & state

How is data fetched?Intermediate

SWR hooks in src/hooks/use-api.ts (useDashboard, useTickets, useTicket, useTeam, useMe, useWorkload) refresh every 30 seconds and on focus, keep previous data while revalidating, and accept an "enabled" flag so a role doesn't fetch data it can't use. useRefreshAll revalidates every /api/* key after a mutation. apiGet/apiSend in src/lib/api-client.ts turn error responses into ApiRequestError (status + server message) and record success/failure for the sync indicator.

src/hooks/use-api.ts:25-90; src/lib/api-client.ts; src/lib/sync-status.ts:6
Where does UI state live?Intermediate
  • URL: the open ticket (?ticket=) and queue filters/sort/page (use-queue-state.ts), so views are shareable and survive refresh.
  • Server cache: everything from the API, in SWR.
  • localStorage: unsent reply and note drafts per ticket (best effort, wrapped in try/catch).
  • React context: shell state (sidebar collapsed, palette open) in shell-context.tsx.
src/features/queue/hooks/use-queue-state.ts; src/features/ticket-workspace/hooks/use-reply-draft.ts; src/components/layout/shell-context.tsx
How does the reply composer's state work?Advanced

useReplyDraft is lifted above the responsive layouts (desktop and mobile render different trees) so they share one state. It keeps separate texts for Reply and Internal note; the reply starts from the pending AI draft (the newest draft with no sent_message_id) or a locally saved edit; Restore AI draft resets it; a "Then set" status defaults to Pending and only offers statuses the server says are allowed (allowed_statuses); Closed tickets block replies but allow notes; a ref-based guard prevents double submission; errors keep the text and map status codes to specific messages. When the ticket changes, state is re-derived during render (React's documented pattern) instead of in an effect.

src/features/ticket-workspace/hooks/use-reply-draft.ts; src/features/ticket-workspace/components/reply-composer.tsx
How are the forms for mailbox and AI settings built?Basic

The mailbox form switches between a status card (connected) and a connect flow with Gmail / Other provider tabs; the Gmail tab is a numbered three-step guide with links to Google's pages. The AI panel shows key status, a verify-and-save form and an accessible switch (role="switch", aria-checked, labelled and described) for automatic replies. Both show server messages inline and never display stored secrets.

src/features/settings/components/mailbox-form.tsx; src/features/settings/components/ai-settings.tsx
What accessibility practices are used?Intermediate
  • Ids from useId because some components render twice (desktop and mobile layouts), so labels and aria-describedby never collide.
  • Labels for every input, including visually hidden ones; aria-invalid and described error messages.
  • Radix-based dialogs, dropdowns and tabs for focus management and keyboard support.
  • aria-pressed on the Reply / Internal note toggle; role="switch" on the auto-send setting.
  • Customer email bodies rendered as plain text, never as HTML.
