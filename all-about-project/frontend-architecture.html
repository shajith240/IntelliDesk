Frontend Architecture

How the React/Next.js frontend is organized: data fetching patterns, state management, the app shell layout, and the feature folder structure. The frontend polls the API every 30 seconds rather than using realtime push.

Data fetching & state

How is data fetched from the API? Are there realtime subscriptions?Basic

The app uses SWR (stale-while-revalidate) for client-side data fetching with polling, not realtime push. Every API fetch is wrapped with a refreshInterval: 30_000 option, and the app revalidates on focus and after mutations. There are no WebSockets, subscriptions, or Vercel KV realtime — just standard HTTP polling at a 30-second interval.

What does the SWR hook suite cover?Basic

Five main hooks abstract the most common API calls: useDashboard() (stats and metrics), useTickets(query) (the queue list with filters/sort/page), useTicket(id) (a single ticket detail — accepts null to skip fetching), useTeam() (active team members), and useRefreshAll() (a function to revalidate every cached /api/* request after a mutation or when the user clicks Refresh).

How does sync status get shown to the user, and what states are tracked?Intermediate

Every API call (via apiGet and apiSend) records success or failure to an external store using useSyncExternalStore, not React state. The store tracks lastSuccessAt, lastError, consecutiveFailures, and browserOnline, and emits to listening components. A selector function deriveSyncState(snapshot, now) derives the user-facing label from the snapshot: "offline" if browserOnline === false or 3+ consecutive failures, "reconnecting" if 1–2 failures, "stale" if no sync in 75 seconds (2.5× the 30s interval), or "synced".

export function deriveSyncState(s: SyncSnapshot, now: number): SyncState {
  if (!s.browserOnline) return "offline";
  if (s.consecutiveFailures >= 3) return "offline";
  if (s.consecutiveFailures > 0) return "reconnecting";
  if (s.lastSuccessAt === null) return "connecting";
  if (now - s.lastSuccessAt > REFRESH_INTERVAL_MS * 2.5) return "stale";
  return "synced";
}

How does the API client handle errors and record failures?Intermediate

apiGet() wraps fetch() and catches network errors and non-2xx responses. When a fetch fails (network down or timeout), it throws ApiRequestError("Network unavailable...", 0) and calls recordSyncFailure("Network unavailable"). When the response is non-2xx, it reads the server's JSON error field (or falls back to statusText), constructs an ApiRequestError with the message and status code, and records the failure. On success, it calls recordSyncSuccess() to reset the consecutive-failures counter.

if (!res.ok) {
  const message = await readError(res);
  recordSyncFailure(message);
  throw new ApiRequestError(message, res.status);
}
const data = (await res.json()) as T;
recordSyncSuccess();
return data;

Layout & shell

How is the app shell structured?Intermediate

The app shell wraps every page and consists of: a sticky TopBar (56px height, always visible), a collapsible sidebar (on desktop, toggleable to the left; on mobile, a drawer Sheet), and a main content area. The shell state (sidebar open/closed, mobile nav open/closed, command palette open/closed) is managed by ShellProvider and useShell(). The sidebar uses localStorage to persist the collapsed/expanded state across sessions. A skip-to-content link is always first in the tab order for keyboard navigation.

How does the ticket workspace stay mounted instead of being a separate route?Advanced

The ticket details panel is not a route; it lives as a slide-over drawer on the same page as the queue list. The open ticket id is persisted in the ?ticket=<id> URL search param via useTicketParam(), so opening a ticket updates the URL without navigating. Closing the param closes the drawer. This pattern lets the user browse the queue while keeping the same URL intact for back/forward and refresh, and avoids unmounting/remounting the queue list when opening a ticket.

export function useTicketParam() {
  const router = useRouter();
  const searchParams = useSearchParams();
  const ticketId = searchParams.get("ticket");

  const setTicket = useCallback((id: string | null) => {
    const params = new URLSearchParams(searchParams.toString());
    if (id) params.set("ticket", id);
    else params.delete("ticket");
    const qs = params.toString();
    const href = qs ? `${pathname}?${qs}` : pathname;
    if (id) router.push(href, { scroll: false });
    else router.replace(href, { scroll: false });
  }, [pathname, router, searchParams]);

  return { ticketId, openTicket, closeTicket };
}

Feature organization

What is the folder structure inside a feature domain?Basic

Each feature lives under src/features/<domain>/ and is subdivided into: components/ (React components used by this feature), hooks/ (feature-specific hooks), and lib/ (business logic, utilities, types). Shared UI primitives live in src/components/ui/, shared hooks in src/hooks/, and shared utilities in src/lib/. The import direction is enforced: app → features → shared. One documented exception: command-center imports queue's WorkQueue component.

src/features/queue/ contains components/ (queue-list.tsx, queue-filters.tsx, work-queue.tsx, queue-skeleton.tsx), hooks/ (use-queue-state.ts), and lib/ (grid.ts) — demonstrating the pattern
How does the queue filter state work with URL parameters?Advanced

useQueueState(scope, pageSize) reads and writes all queue filter, sort, and page state to URL search params. Status, priority, category, search query, sort field, sort order, and page are all persisted in the URL, so filtering survives refresh and back/forward. The hook debounces search input by 300ms to avoid hammering the API while typing. Some scopes (e.g., "incoming") lock the status filter (always "New"), and changes reset the page number to 1.

Performance & constraints

Does the app enable the React Compiler, and what does that mean for state updates?Advanced

Yes, the app enables reactCompiler: true in next.config.ts. The React Compiler (Forget) automatically memoizes component output and fine-grained dependencies, reducing unnecessary re-renders. This introduces one key constraint: useEffect with a sync setState (setting state directly in the effect body, not in a callback) violates the compiler's expectation that effects have no early returns or complex control flow tied to state. Effects must either be properly async or dispatch to a callback (useCallback); any sync setState in an effect body will likely cause a linting error.

const nextConfig: NextConfig = {
  reactCompiler: true,
};

How does the queue table adjust its column layout without breaking responsiveness?Advanced

The queue table uses CSS container queries (@container and @min-[Xpx]:) instead of viewport breakpoints (md:, lg:) to size columns against the table's own rendered width. The ROW_GRID template in src/features/queue/lib/grid.ts defines four breakpoints: 560px (ticket number + severity + title only), 860px (adds customer and AI confidence), 1100px (adds updated-at), and 1240px (adds category). Low-value columns drop in order as the container narrows, so the same component never produces horizontal scroll regardless of whether it's rendered full-width or nested next to a sidebar.

How often does the SLA countdown update on the screen?Basic

The current time is fetched with useNow(intervalMs = 30_000), which re-renders every 30 seconds by default. This is paired with SLA due-date calculations and "x ago" relative timestamps. Calling useNow() with a smaller interval (e.g., useNow(1000) for countdown mode) is possible, but the default is 30 seconds to avoid excessive re-renders.

export function useNow(intervalMs = 30_000): Date {
  const [now, setNow] = useState(() => new Date());
  useEffect(() => {
    const id = window.setInterval(() => setNow(new Date()), intervalMs);
    return () => window.clearInterval(id);
  }, [intervalMs]);
  return now;
}
